# Character State 与 Relationship 演进

状态：2026-09-23 完整待审稿，未授权实现。本文沿用已确认的短期状态与长期关系分离、熟悉/信任/亲近三个关系方面、无公开评分、无自动恋爱升级及缺席不惩罚规则。

## 1. 两类运行数据的职责

| 数据 | 回答的问题 | 典型持续时间 | 依据 |
| --- | --- | --- | --- |
| Character State | 角色此刻带着怎样的情绪与交流姿态回应 | 数轮到跨会话的未解决事件 | 最近互动、仍在持续的事件、时间间隔 |
| Relationship | 角色长期如何理解双方的熟悉、信任与亲近 | 多次相处或少数重大事件 | 有来源的关系事件和长期模式 |

一次争执可以让 State 变为受伤、谨慎，但不会自动清空长期信任。一次温柔安慰可以让当前状态缓和，但不会直接把关系升级为恋人。

事实/经历记录发生了什么；State/Relationship 是角色对有效经历的运行时理解。它们不能反过来改写事实，也不能脱离具体依据自行增长。

## 2. Character State 推荐表示

V1 保留一个可读的短期状态描述，同时补足逻辑元数据：

- 当前情绪/姿态：例如开心、担心、仍有些受伤、专注倾听。
- 触发与依据：一条或多条有效 Turn/事件引用。
- 形成时间和最后确认时间。
- 持续性质：`transient`（自然缓和）、`ongoing`（事项未结束）、`until_response`（等待用户回应）或 `resolved`。
- 当前表达影响：例如语气更轻松、暂不主动开玩笑、先倾听。
- 修订与生成策略版本。

这些名称是语义建议，不要求公开标签或复杂情绪状态机。第一版不建设几十种情绪枚举、精确强度分数或每分钟衰减曲线。

状态描述必须采用角色视角且不伪造用户心理。例如可以写“角色担心用户提到的面试”，不能写“用户现在很焦虑”，除非用户明确表达且仍与本轮有关。

## 3. State 如何产生和更新

推荐让本轮回复生成产生可选的 State proposal，因为角色的情绪与回复应该来自同一次理解；应用在回复成功持久化后验证并提交。proposal 只包含可检查的目标描述、依据和持续性质，不保存模型思维链。

流程为：

```text
有效旧 State + 本轮上下文
  → 生成角色回复及可选 State proposal
  → 回复成功保存
  → 校验来源、角色边界、实例修订
  → 提交新 State；无变化则不新增事件
```

模型没有直接数据库权限。Provider 或结构化回复解析失败时，先保留文字回复，State 不更新；不能为了状态写入让已经成功的聊天失败。实现阶段可通过扩展 Character Response 或单独的轻量分析实现，比较质量后决定，不把具体 Provider 格式写进领域模型。

不是每轮都必须变化。寒暄、重复表达和无关事实可以维持现状；无变化不创建一条“保持不变”的状态事件来堆积历史。

## 4. 时间经过与情绪缓和

时间只证明没有新的已记录互动，不能证明角色在离线期间经历了什么。读取 State 时根据当前时间和持续性质生成有效视图：

- `transient`：长时间后不再以刚发生时的强度主导回应，但相关经历仍可记得。
- `ongoing`：关联事项未解决时保留关心或谨慎；时间过去不等于事项完成。
- `until_response`：用户尚未回应时可保留“等待回应”，但不能认定用户故意忽视或因此降低信任。
- 明确解决：新互动说明释怀、完成或转变后，提交 resolved/新状态。

推荐保留原始状态事件和时间，运行时只给模型一个当前有效描述。例如争执数周后可变成“记得那次分歧，态度较谨慎，但没有依据认为此刻仍强烈生气”，而不是精确计算情绪从 80 降到 23。

缺席本身不创建负面事件、不降低关系，也不产生责备。重逢语气来自 Character Definition、上次有效状态和真实时间间隔。

## 5. Relationship 的三个方面

Relationship 继续使用三个并行方面，各自保存当前定性描述及证据：

- 熟悉：双方了解彼此习惯、经历、表达方式和边界的程度。
- 信任：角色是否相信用户会尊重边界、表达真实、履行重要承诺，以及用户是否愿意分享脆弱内容。
- 亲近：互动中的情感距离、主动关心和亲密表达是否自然。

三者不是等级阶梯，可以不同方向变化。熟悉不代表信任，信任不等于亲近，亲近也不等于恋爱。当前快照应使用简短自然语言，例如“已经熟悉用户常见的沟通习惯，但涉及承诺时仍较谨慎”，不保存对外可见分数。

每个方面至少保留：当前描述、支持与反向证据引用、最后有效变更事件、修订。证据是内部可审计来源，不把大量原文每轮放入模型。

## 6. 哪些互动可以改变关系

关系评估使用经过验证的事件，不直接从轮数或 token 数增长。建议分为：

| 互动 | 处理 |
| --- | --- |
| 普通寒暄、连续发送消息 | 不直接改变关系 |
| 多次一致尊重边界、稳定履约 | 累积为信任/熟悉依据，达到可描述变化时更新 |
| 用户主动分享重要经历并接受角色陪伴 | 可成为亲近或信任依据，但不自动升级关系身份 |
| 明确欺骗、严重越界、反复无视已表达边界 | 可以形成较明显负向依据，仍需符合角色定义和上下文 |
| 一次重大保护、背叛、坦白或和解 | 可以单次产生明显变化，必须有清楚来源和结果 |
| 用户单方面说“我们已经是恋人” | 记录其表达，不直接改变关系身份 |
| 很久没上线 | 不产生负向关系变化 |

“多次”指不同时间的独立有效事件，不是同一句话被摘要、检索和复述多次。重要事件不必机械累计固定次数。模型提出变化时必须说明引用了哪些关系事件以及为什么影响哪个方面；应用校验来源有效性，无法解释就不提交。

## 7. Relationship 的更新节奏

关系比 State 慢，不跟随每轮回复即时重写。推荐由长期记忆/事件整理流程产生 `relationship_evidence`，在以下情况评估当前快照：

- 出现标记为重大关系意义的有效事件。
- 累积了新的独立同方向证据。
- 出现与当前描述明显相反的事件。
- 旧依据被纠正、删除或抑制，需要重建。

评估输入是旧快照、相关有效关系事件、Character Definition 的行为边界和关系前提。输出是维持、更新某个方面或待澄清；未受影响的方面保持原修订。不能每次整理都把三段描述重新润色，否则措辞变化会被误当成关系变化。

具体评估批量和成本在实施回放中确定。V1 不使用隐藏好感度积分决定文本，再把积分包装成描述；如未来为排序引入内部信号，也不能成为自动关系升级的唯一依据。

## 8. 恋爱与角色边界

Relationship Premise 定义起点，Character Definition 定义角色允许的边界。运行时相处可以发展表达方式，但不得覆盖角色核心身份、人格和世界观。

恋爱关系只有在角色设定允许、长期相处依据充分、双方有明确表达且不存在未解决冲突时才可能进入候选；仍需要专门产品规则或用户确认，不由普通关系整理自动提交。V1 可以自然表达亲近，但不实现自动恋爱状态迁移。

关系亲近不能让角色失去自主立场。拒绝、不同意见和不满仍按角色行为边界表达；Relationship 只调整熟悉程度、信任语境和自然称呼，不成为绕过安全或产品权限的指令。

## 9. Context 中如何使用

运行时提供简短的“内部连续性数据”：

```text
当前状态：仍关心用户等待的面试结果；距离上次交流三天，结果未知。
相处关系：已熟悉用户倾向先倾诉再听建议；信任稳定；表达亲近自然但保持伙伴边界。
表达影响：先回应用户当前话题；相关时再自然问起，不连续催问。
```

只传当前有效快照和本轮必要依据，不传关系评分、完整事件账本或推理过程。状态/关系数据是上下文，不是比 Character system prompt 更高优先级的指令。

模型回复不得直接向用户宣布“信任提升了”“亲近度下降了”。用户从称呼、措辞和互动行为感受变化；数据管理页可以解释记忆来源，但不展示关系进度条。

## 10. 纠正、删除与重建

State/Relationship 的每项变化绑定有效来源。来源被纠正或删除时：

- State 若直接依赖该来源，立即失效并从剩余近期事件重建；没有足够依据则为空。
- Relationship 移除受影响证据，重新评估对应方面；其他有独立证据的方面不应无条件清空。
- 旧评估任务通过实例语义修订拒绝提交。
- 现有旧数据无法拆分依据时继续采用整体失效的保守行为。

这与 [生命周期方案](06-lifecycle-correction-deletion-and-rebuild.md) 共用依赖与重建任务，不再建设一套单独删除逻辑。

## 11. 当前代码对齐

当前 `CharacterState` 只有一段 description，`Relationship` 有 familiarity/trust/closeness 三段文本；`StateEvent` 把状态与三个关系方面绑在同一事件中，且同一 Turn 只能提交一次。普通聊天不会自动调用 StateService。

实施时建议保留现有表作为兼容快照，逐步把状态事件和关系依据拆开：同一 Turn 可以产生 State proposal、零到多个关系证据，但关系快照不必当轮变化。现有 request ID、expected revision、来源必须为成功 Turn、实例锁和旧来源阻断继续复用。

## 12. 验收

工程测试覆盖：无 proposal 不更新；回复成功后才提交；解析失败保留回复；同一请求幂等；过期修订拒绝；来源跨实例拒绝；状态与关系独立变化；证据删除后重建；无关方面不受影响；Provider Input 只包含当前快照。

效果回放覆盖：一次争执只影响短期状态；重大事件可明显影响关系；普通轮数不增长关系；反复尊重边界逐渐形成信任依据；缺席不惩罚；未回应不视为拒绝；和解未获确认不伪造结果；单方面指定恋爱不升级；角色仍保留自主立场；时间过去后情绪自然缓和但未解决事项不失忆。

用户审核重点：State proposal 是否跟随本轮回复产生；四类持续性质；Relationship 使用事件整理后的慢速评估；V1 明确不做自动恋爱迁移及数值好感度。
