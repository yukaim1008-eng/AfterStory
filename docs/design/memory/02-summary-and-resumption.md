# 摘要组织、原文选择与离开后续聊

状态：2026-09-21 讨论稿，未授权实现。用户已确认三项共同采用：压缩保留原文、分段摘要配合连续性笔记、压缩来不及时等待或可重试；其余具体规则仍是本轮建议。总方案见 [长会话连续性](01-conversation-continuity.md)，已确认规则见 [V1 基线 5.3](../../decisions/0001-v1-baseline.md#53-长会话连续性方向2026-09-21-确认)。

## 1. “最近”与“没聊完”分开判断

建议同时使用记录定位、时间与话题状态，不能只用“最近 24 小时”或固定轮数选上下文。

| 概念 | 定位依据 | 时间间隔的作用 |
| --- | --- | --- |
| 角色实例 | 当前用户拥有的 `character_instance_id` | 不因离开或跨天而更换 |
| 聊天记录容器 | `conversation_id` | 刷新、关页面或隔天不自动等于新容器 |
| 最近交流段 | 当前记录中有序的成功轮次，辅以真实发言/完成时间 | 长间隔可提示交流中断，用于分段与表达；不决定话题结束 |
| 未完话题 | 明确的话题对象、讨论进度、未回答问题及来源 | 可以隔多个交流段继续；超时不自动完成或取消 |

以上是逻辑区分，不要求第一版新增四套表或自动创建“会话段”实体。一个聊天记录可以持续几个月，包含多个话题；同一话题也能跨同实例的多个聊天记录继续。

## 2. 两种摘要承担不同职责

### 2.1 分段摘要：这一段发生过什么

按相邻成功轮次分段，在容量范围内尽量靠近话题转折。一个分段可能含几个话题，每项内容关联其原文来源；不强行要求“一段只能聊一件事”，也不把跨段的同一话题当成多件独立事件。

建议每段组织为：

- 来源：实例、会话、实际成功轮次/消息引用、已知时间范围、修订和摘要版本。
- 话题与对象：人物、事件或候选方案，必要时说明别名和指代。
- 经过与变化：谁说了什么；建议、确认、拒绝、替代或取消的先后。
- 暂时结论：明确达成的结果，不把未回应当成接受。
- 未完交流：什么还没说完、谁在等哪条回应、用户是否要求暂不讨论。
- 互动依据及精确片段：有来源的情绪表达、称呼、日期、数值与关键原话引用。

分段摘要属于历史记录。比如“当时约定周五面试，后来改为周一”应保留变化，而不是把旧段无痕改成从来都是周一。检索时还需检查后续更新，不能只读旧段就把旧计划当现状。

### 2.2 连续性笔记：现在接着聊需要知道什么

按话题维护少量当前进度：话题对象、最新有效结论、尚待回应的点、最后相关发言、是否适合主动提起，以及所引用的摘要和原文。下面为语义样例，不是最终数据库字段：

```text
话题：用户准备告诉同事一件事，仍在斟酌措辞
目前进度：比较了 A / B 两种说法，用户更倾向 B，尚未决定发送
最新原话：用户说“我先吃个饭，回来再说” [来源消息]
角色最后回应：请用户回来后补充最担心对方如何反应 [来源消息]
待继续：用户尚未说明最担心的反应；也未说明已发送
阶段：暂搁，等待用户继续
时间：来源中的真实时间；未知则标为未知
回读入口：A / B 原文及最后一个完整问答 [来源范围]
```

“进行中、等待补充、暂搁、已结束”可以作为候选语义状态；具体字段稍后决定。用户离开、话题被切走、明确说“不聊了”分别记录，不能混为同一种结束；明确不希望再被问起时，停止主动提起，用户自行重开时再据新输入处理。

模型可提出分段与笔记更新，应用负责核对来源、状态转换依据和修订后保存。更新时间与最后相关发言时间分开；重生成摘要不表示这件事刚刚又发生过。

## 3. 排序与时间信息

建议规则：

1. 先限制到正确的用户和实例，再尊重用户当前打开/选定的 `conversation_id`。不要因为另一会话更新时间更新，就替换当前对话。
2. 同一会话内用 `Turn.sequence` 还原已提交成功问答的顺序。时间相同或客户端时钟错误不能改变既有轮次顺序。
3. 同实例跨会话需要比较最近交流时，依据实际交互时间；时间相同用稳定 ID 保证排序稳定，不把 ID 当成实际时间或因果关系。
4. 时间戳用于告知模型当前时间、上次相关交流时间、已过去多久，以及解析“昨天”“明天”。区分原话告知时间与所谈事件的发生/计划时间。
5. 服务端保存可比较的时间，按用户时区解释自然语言日期。没有可靠时间/时区时保留未知或不确定范围；“下午”不能强行补成某个精确时刻。
6. 打开页面、摘要生成、数据库更新和失败重试时间，不自动当成用户刚与角色交流的时间。长时间未发消息只证明没有新消息，不能断言用户一直离线。

消息虽可能传给模型为普通文本，组装层仍需用清楚的数据块提供本轮时间及相关历史时间，不能要求模型从“最近几条”自己推断时间。时间数据属于 Runtime Context，不写入冻结的角色定义。

间隔阈值只用于提示“可能开始新一段交流”、压缩边界和语气。暂不决定“超过多少分钟就是新会话”，更不能据此删除未完话题。

## 4. 什么时候传原文

| 场景 | 建议提供的原文 | 配套材料 |
| --- | --- | --- |
| 正在连续聊天 | 预算内当前会话最近的完整连续问答 | 相邻较早部分的摘要、必要话题笔记 |
| 离开后回来续聊 | 上次停下处最后一个完整问答，必要时扩展相邻几轮 | 话题进度、上次时间、本轮时间、未回答点 |
| 提到“第二个”“那句话”“你当时怎么说” | 能解释指代或支持准确引用的原文及必要邻近发言 | 有关摘要和后续更正/取消 |
| 切到新的无关话题 | 当前输入及必要的最近问答，不强行加载整段旧讨论 | 旧话题保留在可检索笔记里，避免抢占新话题 |
| 远期普通背景，仅需要大意 | 不必为了“记得”就传整段原文 | 先用可靠摘要或事实；需要核实再下钻 |

近期是顺序上的连续后缀，不受“过夜即过期”限制；选择多少由 token 预算和依赖范围决定。即使最后两轮是三天前，用户回来仍可能是在回应那两轮，应保留时间背景来解释。

定向取回的旧原文放在明确的历史资料块，保留来源、说话方与时间，不伪装成当前对话刚发生的消息。与近期原文和摘要去重。所有选择均服从现有修订/删除边界；关键依据无法获得时不能靠猜测补齐。

## 5. 用户回来时如何续接

建议在恢复页面时准备候选材料，在下一次实际生成回复前结合用户最新输入作最终选择。仅仅打开页面不自动新增一条角色消息；欢迎消息和线上提醒的主动触发仍归单独讨论，不能在此隐含确认。

| 用户回来后的输入 | 处理建议 |
| --- | --- |
| “继续刚才那件事”“B 那个说法我想改一下” | 优先对应话题，回读停下处及指代原文，接着处理 |
| “我回来了” | 若只有一个明确未完且适合提起的话题，可自然承接；不要把所有待办逐条盘问 |
| “继续吧”，但之前同时有多个未完话题 | 找不到唯一明确指向时，用自然语言简短澄清 |
| “今天发生了另一件事” | 先回应新话题，旧话题暂搁而非自动结束 |
| 几天后问起早先计划 | 带实际时间与最新已知进展；不能把已过日期仍称为“明天”，也不能假设计划已经完成 |

例：周五角色问“你最担心同事怎么回应”，用户关了页面；周六回来答“我怕他觉得我在推卸责任”。即使没有说“继续”，应依据上次问题、当前语义和话题进度识别为补充答案。若语义也符合另一个话题，则澄清，不能仅因时间最近就强行归属。

模型得到的应是“上次停在这个问题，至今没有记录到答案；现在用户这样回答”，而非只有“用户曾讨论过同事”。与此同时，用户未回复不等于拒绝、同意或情绪转坏，已生成回复也不证明用户读过它。

## 6. 恢复依据不能依赖正常退出

每个成功轮次已经持久化原文和稳定顺序。摘要/笔记保存其处理到的来源位置；用户回来时读取该位置之后的成功原文，修补摘要滞后。需要先补做压缩才能满足预算时，沿用已确认的等待/重试策略。

关页面、断网、切标签页或进程退出都可能没有可靠的“结束事件”，因此不能等用户点击退出才保存总结。页面打开也不是自动宣告旧事项已关闭的信号。

页面草稿或失败轮中的未完成请求不能当作角色已经理解过的完整交流。恢复时继续沿用现有草稿/重试行为；只有成功提交的问答进入自动分段摘要。成功写入但尚未被用户读到的回复可以作为历史记录，不能据此假设已获用户回应。

## 7. 当前代码需要对齐的点（只读发现）

- 前端 `openChat` 通常使用已保存的会话 ID，并可从历史恢复指定会话；这意味着“回来”一般沿用同一个 Conversation。该定位行为应优先保留。
- 无保存 ID 时调用 `/sessions/open`；后端目前按 `Conversation.id` 选择一个已有会话，不是按最近交流时间。若未来要求恢复最近会话，需要单独明确主实例选择与最近活动规则，不能直接按角色跨实例合并。本轮不改变实例选择策略。
- 历史目录的 `last_activity_at` 使用 `Turn.updated_at/created_at`，包含失败轮与重试更新，适合当前列表活跃排序，但不能未经筛选就作为“最近成功交流”或“用户离开时间”。
- `Message` 当前没有独立发言时间；`Turn` 有创建/更新时间，旧数据可能为空。需要更精确的告知/完成时间时应明确补充契约，不能伪造历史时间。
- `ContextAssembler` 尚未提供当前时间、摘要、未完话题或恢复逻辑。上述均为设计目标，不是现有能力描述。

## 8. 本轮增加的验收案例

| 输入 | 预期 |
| --- | --- |
| 聊一半关闭页面，隔天直接回答上次问题 | 接住指代，知道时间有间隔，不要求先说“继续” |
| 返回时摘要任务尚未完成 | 使用已保存原文补齐，不把工作中的摘要当完成，不丢最后几轮 |
| 最近发言只是寒暄，而未完话题在更早位置 | 能依据当前输入找到正确话题；不只按最后更新时间取摘要 |
| 多个话题交错，返回说“继续” | 明确时续接，歧义时澄清，不随机合并 |
| 昨天说“明天下午”，两天后再来 | 知道计划时间已过，不假设完成或擅自顺延 |
| 用户要求不再主动问某件事，之后寒暄或聊新事 | 保持该边界，不因话题未完成每次催问 |
| 用户显式打开较旧会话，另一个同实例会话更新更晚 | 当前记录定位不被偷偷替换，相关其他经历有来源地按需读取 |
| 摘要重建或失败请求重试改变更新时间 | 不把老事件当作刚发生，不据此认定用户刚参与了成功交流 |

本轮只确认此前三项总体方向并提出上述具体组织建议，不确认摘要字段、话题识别模型、时间阈值、数据库结构或开发阶段。
