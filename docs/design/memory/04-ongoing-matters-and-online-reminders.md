# 持续事项与线上提醒

状态：2026-09-23 完整待审稿，未授权实现。已确认阶段范围是先支持 AfterStory 打开时的线上提醒；应用关闭后的调度和系统通知留到后续 Tools/通知编排。本文给出 V1 推荐方案，用户审核前不视为产品决策。

## 1. 为什么持续事项不能只是一条长期记忆

长期事实和经历用于回答“知道什么、发生过什么”；持续事项用于回答“还有什么没有结束、下一步是什么”。提醒则是持续事项上的一个投递要求。三者可以关联，但生命周期不同。

| 类型 | 例子 | 是否需要到期时间 | 完成方式 |
| --- | --- | --- | --- |
| 待办 | 下周交申请材料 | 可选；没有日期也可持续跟进 | 用户说明完成，或显式取消 |
| 等待结果 | 用户在等面试结果 | 可选预计日期 | 用户告知结果后完成并可生成经历 |
| 约定 | 下次继续讨论旅行方案 | 通常不需要精确日期 | 讨论完成或用户取消 |
| 提醒 | 周二 9 点提醒交材料 | 必须有足够精确的触发时间 | 投递不等于事项完成 |
| 角色承诺 | 角色答应下次先问进展 | 可有条件或时间 | 实际履行、撤回或失效 |

一个事项可没有提醒；一个提醒必须归属一个事项或明确的独立提醒内容。事件不能因为到了计划日期就自动变成“已经发生”。

## 2. 推荐的数据语义

以下是逻辑契约，不是本轮确定的表字段：

- 归属：明确的 CharacterInstance；同一用户的其他角色默认不知道。
- 内容：用户要做、等待或继续讨论的具体事项。
- 类型：待办、等待结果、约定、提醒或角色承诺。
- 状态：`open`、`completed`、`cancelled`。过期不是终态；只是当前时间超过计划时间但尚无结果。
- 时间：计划时间或范围、提醒触发时间、时区、时间精度与原表达。
- 下一步：谁需要做什么，或等待谁提供什么信息。
- 主动提起策略：允许主动提醒、仅相关时提起、用户回来时可询问、不要主动提起。
- 来源与修订：创建、改期、取消、完成及恢复的消息依据。
- 关联：相关事实、经历和后续生成的结果事件。

提醒必须使用可计算的触发时间。只知道“下个月”“有空时”可以保存为持续事项，但不能伪装成已经创建了定时提醒。用户时区未知或“周二”存在歧义时，需要自然确认后再承诺提醒。

第一版建议只支持单次提醒。周期提醒、复杂工作日历法、外部日历同步和地理围栏留到 Tools 阶段；数据边界允许未来增加 occurrence，不提前实现完整日历系统。

## 3. 提取与确认

对话整理模型可以提出以下操作：

- `create_matter`：新建持续事项。
- `create_reminder`：为事项建立准确的提醒时间。
- `reschedule`：改期，保留旧时间和改期依据。
- `complete`：用户明确表示已经完成或结果已经出现。
- `cancel`：用户取消事项或不再需要提醒。
- `change_policy`：例如“这件事别再主动问”。
- `no_change`：只是在假设、讨论建议或复述，不提交状态变化。

“我下周要交材料”可以形成待办；“下周二九点提醒我交材料”同时形成提醒请求。“你到时记得提醒我”但没有可计算时间时，只能形成待确认请求，角色不能回答已经设好提醒。

明确提醒、改期、取消和完成属于高确定性操作。应用核验时间、来源与当前修订并成功提交后，角色才能确认结果。普通计划可以后台整理；不能让后台失败后仍留下“放心，我会提醒你”的承诺。

模型不能仅因日期过去就推断完成，也不能从“我考虑报名”提取成确定待办。角色提出的建议只有在用户接受后才成为用户事项；角色自己的承诺必须来自已经保存的角色回复，且不能超出当前系统能力。

## 4. 状态变化

```text
创建 open
  ├─ 用户完成 → completed
  ├─ 用户取消 → cancelled
  └─ 改期/补充 → 仍为 open，产生新修订
```

超过计划或提醒时间只形成 `overdue` 读取视图，不直接改变为 completed/cancelled。用户之后说“已经交了”，事项完成，并可生成一个带真实时间精度的经历；不知道完成日期时不拿告知日期冒充发生日期。

改期保留原计划及来源，新时间成为当前有效值。取消提醒不必取消整个事项；取消事项则撤销尚未投递的提醒。完成后默认不再提醒，除非用户明确建立新的后续事项。

同一句“下周再提醒我”若指向当前事项则更新它；不能每次生成新事项。无法确定指向哪个事项时先澄清，不按标题相似度随意修改。

## 5. 线上提醒的触发与投递

V1 推荐由服务端保存提醒及投递记录，前端只负责在在线状态请求到期项并呈现。检查入口包括：

1. 应用启动或重新回到前台。
2. 进入某个角色实例时。
3. 应用保持在线时的轻量周期检查。
4. 用户发送消息前的运行时准备，用于让角色在本轮自然提及已到期事项。

前三个入口共用同一个“领取到期投递”服务，第四个入口读取已经到期且尚未恰当处理的事项。不得在四处各自判断并重复生成提醒。

第一版呈现建议使用角色归属明确的站内提醒卡片或通知项；有活动聊天时，下一次回复可以获得该提醒上下文并自然提及。仅打开页面不强行插入一条伪装成普通问答的历史消息，也不要求为主动消息重构现有 Turn 结构。未来若增加真正的角色主动消息，应以明确的 `origin=reminder` 记录，并复用同一投递幂等键。

提醒内容可以按角色语气呈现，但时间、事项和投递状态来自结构化数据。润色模型失败时仍可显示准确的基础提醒，不能因角色文案生成失败错过投递。

## 6. 错过时间、补提醒与防打扰

应用关闭期间不执行通知，但提醒仍保存在服务端。用户下次上线时：

- 到期但从未投递：补发一次，明确已经过期多久或使用实际日期，不再称为“马上到点”。
- 已投递但没有完成：不在每次打开、每轮聊天重复提醒；由主动提起策略决定是否在之后温和跟进。
- 同时积压多项：合并为一个站内入口，优先展示最近到期和用户标记重要的项目，不连续刷出多条角色消息。
- 已取消、已完成或已改期的旧 occurrence：不能补发。

防重复使用稳定投递键，逻辑上至少包含 `reminder_id + schedule_revision + occurrence + channel`。同一到期项被启动、前台恢复和周期检查同时发现时，只允许一个调用领取成功。改期产生新 schedule revision，旧时间的未完成投递失效。

投递记录区分 `reserved`、`delivered` 和 `failed`。领取后前端没有确认展示时不能永久当作已经送达；租约过期后允许安全重试。送达只表示界面成功呈现，不表示用户读过、同意或完成事项。

## 7. 主动关心与正式提醒分开

“面试结果怎么样了”可能是自然关心，不等于定时提醒。持续事项的主动提起策略建议分为：

- `due_only`：只在明确到期时提醒。
- `when_relevant`：聊天自然相关时可以提起。
- `on_return`：用户回来且没有更优先的新话题时可问一次。
- `suppressed`：不主动提起，但用户主动询问时仍可读取。

具体名称不是最终 API。策略必须保留用户的“不再问这件事”。未完成事项不应占据每轮对话，也不能因用户长时间未出现产生责备或关系惩罚。

## 8. 与其他分区的接口

- 长期记忆：保存事项背景和明确偏好；事项本身拥有独立状态，不靠改写事实正文管理完成与取消。
- 经历：事项产生真实结果后，可形成带来源的经历并关联原事项；计划日期不能作为实际完成时间。
- 摘要/连续性笔记：可以记录讨论进度和待回答问题，不负责调度和投递。
- 召回：当前相关、即将到期或已经到期的事项有较高优先级；已完成事项通常按经历召回。
- State/Relationship：没有回应提醒不自动降低信任；角色履行承诺可以成为关系依据，但投递记录本身不等于关系变化。
- Tools/离线通知：未来调度器和通知渠道消费同一 reminder/occurrence，不重建另一套事项数据。

## 9. 失败与边界

- 时间解析不确定：保存待确认事项，不创建精确提醒。
- 提醒持久化失败：明确返回失败，不说已经设置。
- 线上检查失败：不修改投递状态；恢复后重试。
- 文案生成失败：展示结构化基础提醒。
- 用户跨时区：已经绑定绝对时间的提醒保持明确语义；“当地早上九点”类型需显式记录随时区还是固定时刻，第一版可要求确认。
- 重复请求或网络重试：相同操作幂等；相同请求 ID 携带不同时间返回冲突。
- 删除来源或用户要求忘记：交给生命周期规则决定事项、投递和衍生经历如何撤销，不允许待执行任务绕过删除。

## 10. 当前代码对齐与验收

当前代码没有持续事项、提醒、投递表或在线调度入口；Conversation 只支持用户消息触发的 Turn。V1 推荐先采用站内提醒记录，不把主动角色消息硬塞入现有问答结构。现有前端轮询/前台恢复能力需要实施阶段再核对，本轮不改前端。

测试至少覆盖：精确时间创建；模糊时间不虚假承诺；跨时区解析；改期使旧 occurrence 失效；取消提醒但保留事项；完成后停止提醒；应用关闭后上线补发一次；多入口并发只投递一次；领取后展示失败可重试；已投递不等于已读或已完成；多个到期项合并；不主动提起策略；跨实例隔离；删除期间排队任务不能投递。

用户审核重点：第一版是否只做单次提醒；站内提醒卡片加下次回复自然提及的呈现方式；四类主动提起策略；模糊时间是否必须确认。
