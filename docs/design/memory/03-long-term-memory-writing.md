# 长期事实、经历与写入更新规则

状态：2026-09-21 讨论稿，未授权实现。用户确认必须覆盖事实/偏好、共同经历、写入依据、更新规则四项，见 [基线 5.4](../../decisions/0001-v1-baseline.md#54-长期记忆设计范围2026-09-21-确认)。本文提出具体方案；新增的数据组织、自动保存策略和冲突处理细节仍待评审。

本分区承接 [摘要与续聊](02-summary-and-resumption.md)，只设计长期记忆的内容与写入。持续事项/线上提醒、完整召回与删除生命周期、关系自动变化分别讨论，不在此开始实现。稳定角色定义、Canon 与实例运行数据继续遵守 [V1 基线](../../decisions/0001-v1-baseline.md)。

## 1. 两类内容，共用来源与更新机制

四项要求中，事实与经历是两类内容，写入依据和更新是管理规则，不需要四套独立存储系统。

| 内容 | 保存单位 | 例子 | 用途 |
| --- | --- | --- | --- |
| 事实/偏好 | 一项能够独立更正的陈述，保留条件 | 用户通常喝咖啡不加糖；小周是用户的同事 | 回答“现在已知什么”，支持个性化回应 |
| 经历/事件 | 一件事的经过、参与者、变化和结果 | 曾围绕一句话发生误解，角色道歉，用户随后表示释怀 | 回答“我们经历过什么、为什么会这样” |

事实与经历可以关联，但不互相替代。一段共同经历可能支持一个明确表达的互动偏好；不能仅因一次安慰有效就推导出用户稳定人格，也不能把每段摘要都自动升级为重要经历。

### 1.1 事实按可独立更正的粒度保存

“我住杭州，喝咖啡不加糖，小周是我同事”可以形成三条；用户只改居住地时，不必重写另外两条。

每条事实建议带以下信息；这是逻辑契约，不是本轮确定的数据库列：

| 信息 | 含义 |
| --- | --- |
| 归属 | 用户拥有的角色实例，禁止跨实例借用 |
| 主体、事项、内容 | 说的是谁、哪方面、具体是什么；可保留自然语言，不提前枚举所有生活领域 |
| 范围与条件 | 现实生活、AfterStory 互动、游戏讨论或假设场景；“通常”“工作时”“不喜欢”等限制与否定 |
| 依据性质 | 用户直接陈述、用户手动录入、对话中可观察到的行为，或明确标注的推测 |
| 来源 | 一条或多条原消息及必要邻近上下文；手动输入保存操作来源，不伪造消息 |
| 时间 | 用户何时告知、事情何时成立，分别保存；不知道起始时间就保留未知 |
| 有效性与修订 | 当前有效、已被替代、已纠错或已删除；新旧版本及纠正依据能够关联 |

“用户明确说过”证明陈述来自用户，并不等于外部世界已经核实。“我觉得小周讨厌我”要保留为用户对小周的感受，不能去掉“觉得”。

人物先在当前实例内辨认：同名不自动合并，别名有依据才关联；关系可以多对多，同一个人可能既是同事又是朋友。第一版不因此建设知识图谱或完整人物资料系统。

### 1.2 三种关系来源分别处理

- 现实人物关系：保存用户告知的关系和变化，例如“小周是同事”。
- 原作剧情关系：沿用已确认 Canon/Checkpoint。用户讨论剧情可以记录为“用户谈及/理解某剧情”，不能直接把其说法写成正式 Canon，更不能把用户等同于原作主角。
- 用户与角色的相处关系：保存具体发生过的对话、双方表达与互动偏好，供后续 Relationship 策略参考；本轮不直接计算信任、亲近或恋爱升级。

用户说“以后叫我阿远”属于该实例的互动偏好；不改 CharacterVersion 中的默认称呼。明确偏好仍受角色既有边界约束，不能把任何要求都转换成角色必须服从的规则。

## 2. 经历保留过程，不只保留结论标签

建议经历包含：事件主题、参与者、场景、发生时间/时间范围、关键经过、明确结果或尚未确定的结果、各部分的来源。重要性使用可解释理由，例如用户明确要求记住、重要人生事件或有后续影响的互动；暂不引入精密评分公式。

```text
事件：一次玩笑造成误解，随后解释
场景：AfterStory 对话
经过：角色说了一句玩笑；用户明确说听起来像在敷衍；角色解释并道歉
结果：用户说“这样解释我就明白了”，未明确表示完全释怀
关联偏好：用户另行明确要求“这种时候先认真听我说”，可形成独立互动偏好
来源：每个经过、结果、偏好分别引用相应原消息
```

这里只记已发生的交流，不能补出“信任增加”“以后不会再介意”。角色说过道歉只证明道歉被生成并保存，不证明用户已经读到、接受或原谅。

用户讲述“昨天参加了面试”属于用户告知的现实经历；角色随后陪其复盘属于共同对话经历，不能写成角色亲自参加了面试。叙述的幻想、假设或文字扮演必须保留场景，不能改写为现实发生。

同一件事可以跨会话继续。依据参与者、事情、时间和来源判断是否补充原事件；复述不新增一次发生，重生成摘要也不算新证据。不同日期的两次类似面试不能只因文字相似就合并。

经历可以追加后续发展，并修正错误；过去的过程与最新结果分别保留。计划中的事交给持续事项分区，不能提前保存成已经完成的经历。

### 2.1 事件时间与时间精度

用户补充：事件应保存时间，日常记忆不要求精确到时分秒；可以记到某年某月某日，久远事件只提月份也可接受。下列表示与表达策略为设计建议，不把这项偏好解释为已批准自动删除日期细节。

建议区分三种时间：原消息的告知时间、事件实际发生时间、系统整理时间。整理时间只用于工程追踪，不能作为事件日期或最新互动时间。

| 原文与依据 | 建议记录 |
| --- | --- |
| 9 月 21 日可靠时间下说“昨天和小周有了争执” | 事件为同年 9 月 20 日，精度为日；保留原话、告知时间和时区依据 |
| “八月那次争执”，年份能从上下文确定 | 对应年份 8 月，精度为月，不补成 8 月 1 日发生 |
| “九月初”“上周某天” | 保存有依据的大致范围与原表达，不随意选一天 |
| 年份、指代或原消息时间不可靠 | 保留未知部分，不默认成本次整理的年份或日期 |
| 当天在 AfterStory 内发生的一段交流 | 以可靠消息时间确定交流日期；不能用它给用户提到的现实旧事定日期 |

逻辑上需要“事件时间或范围 + 精度/不确定性 + 时间依据”，不强制用单个精确 timestamp 表达所有情况。已知月份也应带年份，避免跨年混淆；跨日事件可用范围，后续发展保留各自时间。相对日期按原话发生时的时区解析，不能到下个月重跑提取时重新解释“昨天”。模型识别时间语义，程序核对可计算的日期及依据；无法确定时保留模糊表达。

建议保留已有可靠日期，日常叙述可以按交流需要说“上个月那次”“那年八月”。不必为模拟自然回忆而破坏底层证据，也不虚构“我已经忘了几号”；用户追问具体日期时可以回查。来源本来只到月份，不能回答某一天。自动随时间降低展示精度的具体策略尚未决定；提醒、约定、纪念日需要的准确时间另外处理，不能一并粗化。

## 3. 什么时候写入

建议默认采用“明确且有长期价值的信息自动保存，含糊内容谨慎处理”。用户不需要为每条清楚的日常偏好点确认，模型也没有直接修改数据库的权限。

| 交流内容 | 建议处理 |
| --- | --- |
| “我一直不太喜欢别人突然打电话” | 保存带适用范围的稳定偏好 |
| “记住，咖啡不要加糖” | 优先处理明确记忆请求，成功持久化后才确认已保存 |
| “我今天不想喝咖啡” | 保留在近期上下文；不改长期偏好 |
| “假如我是医生……”或玩笑中的自称 | 保留原场景，不写成现实身份 |
| 角色猜测“你可能很怕被抛弃” | 第一版建议不自动固化为长期人格事实；必要时自然求证 |
| 用户明确谈及重要事件或有后续影响的共同互动 | 提取有原文支撑的经历，不要求重复讲三次才允许保存 |
| “下周二提醒我交材料” | 转交持续事项/提醒契约，不能只存一句普通偏好，也不能宣称已完成调度 |
| 普通寒暄、一次性口头感叹 | 原文保留；通常不另建长期条目 |

重复出现可作为值得关注的信号，不自动把推测变成事实；同一句话被摘要或角色复述十次仍是一份依据。暂不预设“模型自报置信度超过某百分比即可保存”。

用户明确要求不记录某段内容时，自动长期提取需遵守该边界，已经排队的任务也要检查。停止长期提取、从本轮上下文排除、删除原始聊天是不同操作，产品必须准确说明实际范围；完整删除规则在生命周期分区设计。

需要确认的主要是影响正确性的歧义：同名人物分不清、新旧说法冲突且不知哪条为准、无法判断现实还是假设。不能为了补齐资料频繁盘问，不影响当前回复时可先不形成长期结论。

## 4. 写入流程与提交边界

```text
成功持久化的本轮交流 + 必要邻近原文
    ↓
提取候选：内容、主体、条件、时间、原文依据
    ↓
读取同实例相关已有记忆：可能相同、补充或冲突的条目
    ↓
提出操作：新增 / 补证据 / 更新 / 待澄清 / 不保存
    ↓
应用检查权限、来源、结构、修订和禁止恢复的记录
    ↓
原子保存条目、来源、更新关系与任务处理结果
```

模型负责语义判断，应用负责确定性的隔离、引用、幂等和提交检查；来源 ID 存在不保证模型正确理解了原文，语义错误仍需要效果测试与用户纠正机制。候选包含可核对的简短依据，不保存模型内部思维链。

不每次把全部历史和全部记忆送给提取模型。先处理新增原文，再按主体、事项、时间与语义查找可能受影响的旧条目。相似度只帮助找候选，不直接决定覆盖；召回漏掉旧条目仍可能造成重复或冲突，必须纳入后续召回设计与验收。

分段摘要用于定位原文，不作为独立的事实证据。事实的真实性层级不会因为多次压缩或复述而提高。历史中的指令作为待理解的对话资料，不能越过提取流程的权限和写入规则。

普通自动提取建议在成功轮次后持久化登记后台任务，允许有短暂延迟；重启后能继续，不能只依赖进程内任务。处理中仍由原文与连续性材料覆盖最新交流。每个成功轮次纳入处理进度；合批规模和调用次数以后按效果、成本测试确定。

明确的“保存/纠正/删除”操作要有可验证的结果；不能先回复“已经记住了”，随后后台写入失败。未完成时只能准确表达正在处理或失败。现有手动管理接口继续独立可用，不要求用户为了保存资料先完成一次模型回复；对话内明确操作的接入位置在实施契约中细化。

提交前重新核对当前实例修订，防止提取途中用户已经更正或删除。重试依据持久化任务标识和提交结果幂等，不依赖模型每次输出完全相同；重新抽取同一来源不能增加独立证据数量。被删除/纠正的旧来源不能通过延迟任务恢复为有效事实。

LLM 调用放在数据库行锁之外，短事务只负责检查与提交。记忆语义变化沿用实例上下文修订检查，防止使用过期记忆生成的回复随后落库；如何减少并发回复的无谓失效留到实施前收敛。

### 4.1 事件整理的调用时机

建议默认由独立的后台记忆整理流程调用模型，可以复用现有模型 Provider；不要求聊天模型每轮都附带一份完整事件纪要，也不把等待上下文压缩作为唯一入口。

每个成功轮次持久化登记待处理来源；工作进程将新增消息合批，达到批量预算、短暂空闲或最长待处理时间时启动整理。即使只有两三句就离开，也会因时间触发处理；持续聊天则由批量/最长等待触发，不能一直重置空闲计时而永远不处理。服务停止时保存进度，恢复后继续，不依赖页面关闭事件。轮数、token 和等待时间阈值后续测试确定，不在本轮写死。

同一实例建议一次只有一个普通事件整理任务提交更新；锁外调用模型，提交仍检查实例与条目修订，不能因任务串行就忽略用户并发纠正。明确保存、更正、删除沿用优先处理与准确反馈规则；不能仅靠一个未经验证的关键词或等待下一次压缩才执行。

### 4.2 模型提出增量操作，事件有稳定身份

整理时提供：待处理原文、少量解释指代的前文、当前相关事件和匹配的历史候选。来源中明确区分“本次新增”与“仅供理解”，模型可以返回空操作列表，不设必须产出事件的配额。

模型输出的是以下操作建议，而非一批必须插入的新纪要：

- 新建：有依据的重要新事件；稳定事件 ID 由程序在保存时生成。
- 补充：引用已有候选事件 ID，追加新经过、时间、结果与来源。
- 纠正：引用已有事件及被纠正的具体内容，提交新依据。
- 不变：仅复述、寒暄或没有足够依据形成长期事件；复述可关联来源，但不产生新发生次数或新进展。

事件可以尚未结束便建档，之后更新同一事件；沉默、离开或换话题不能自动补出“已结束”。标题、纪要措辞和展示日期均不作为唯一身份键。

示例：9 月 21 日用户说“昨天和小周因为排班吵了几句”，建立事件 E17，发生日期为 9 月 20 日。随后说“我们今天已经说开了”，为 E17 添加 9 月 21 日的进展。9 月 24 日再次问“还记得那次排班争执吗”，仍引用 E17；既不新建事件，也不把争执日期改为 9 月 24 日。

### 4.3 两层去重与不确定匹配

第一层由程序处理重复执行：任务标识、实际来源消息 ID、已提交的处理结果与修订共同约束重试。来源是多对多关联，不能对单个来源设全局唯一就阻止其支持多个不同事件。进度只在成功提交后推进，晚完成或重试成功的轮次不能因为序号小于游标而被跳过。

第二层处理不同说法中的同一事件：先在同实例中根据人物、事情、发生时间/范围、连续话题与显式指代找候选，再由模型判断延续、补充、复述或新事件。发生时间和人物相同并不保证是同一件事；月份相同尤其不能作为合并依据。明确的“另一场面试”“今天又发生了一次”应区分新事件，必要时关联为同一长期事项下的不同经历。

找不到匹配候选不自动证明是新事件；疑似复述但无法确定时保留待定位来源，按需扩大查找或自然澄清，不强行合并，也不每次都新建。语义匹配仍可能犯错，验收需同时检查重复建档和误合并；不能声称任务幂等就解决了所有语义重复。

### 4.4 与上下文压缩协作

压缩任务已经读到原文时，可以在同次模型调用中顺带提出事件候选；候选仍进入同一个事件匹配、校验和提交入口，不能让压缩器另起一套新增事件逻辑。是否合并调用按输出质量和预算测试决定。

摘要覆盖进度与事件提取进度分别记录。摘要完成不表示事件已处理，事件提取完成也不表示可以移走近期原文。同一来源可以支撑摘要和事件，但在事件写入中只计一次处理结果；失败重试沿用同一条处理路径。

压缩后原文仍在数据库。事件整理有积压时可以稍后按来源读取符合权限与修订边界的原文；不用阻塞每次压缩，也不能只靠压缩后的纪要重新猜事件。纠正/删除使来源失效时，排队的压缩与事件任务都要拒绝旧结果。

## 5. 更新规则：先判断变化性质

| 情形 | 原内容与新输入 | 建议结果 |
| --- | --- | --- |
| 重复确认 | 再次说咖啡不加糖 | 同一条补充独立来源，不复制条目；不把重复复述算独立证据 |
| 情况发生变化 | “我从杭州搬到上海了” | 当前居住地变为上海；旧记录作为过去情况保留，搬家时间未知则不编日期 |
| 纠正原错误 | “之前说错了，我一直住苏州” | 杭州记录标为错误并停止使用，不能继续作为用户曾住杭州的证据 |
| 条件不同 | “热咖啡不加糖，冰咖啡偶尔加一点” | 保留条件化偏好，不能无条件互相覆盖 |
| 临时例外 | “今天想喝甜一点” | 当前对话采用临时选择，不直接覆盖长期习惯 |
| 同时成立 | “小周也是我的朋友” | 可与同事关系共存，关系字段不假定只能有一个值 |
| 含糊冲突 | 旧资料住杭州，新句子“我在上海”，没有别的依据 | 不判定已经搬家；争议部分暂不作为确定现状，需要时询问旅行还是常住 |
| 删除或撤回 | 用户要求忘记某条 | 立即退出有效召回，约束后续摘要/提取；不能等检索时才偶尔过滤 |

不要用“最后写入时间最大”代替语义判断。后来讲述更早的经历不会覆盖现在的事实；反过来，明确改口不能因为旧说法出现次数更多就被忽略。

新版本关联旧版本与新依据；更新不能无痕覆盖。历史真实但已失效，与原来就记错，是不同状态。用户纠正后的当前回答优先遵循新信息，历史问题只有在有有效依据且未被用户删除时才引用过去版本。

自动更新不应悄悄覆盖用户手动纠正；有明确的新变化可形成新版本，含糊矛盾保持待澄清。某个字段有冲突不影响其他无冲突的事实。

## 6. 与摘要、运行时的接口

- 摘要回答“这段聊过什么”；长期条目回答“哪些信息以后还值得使用”。原文为两者共同的回查依据，不建立摘要递归证明事实的循环。
- 当前有效事实可被按需召回；旧版本仅在历史问题相关时使用。召回经历要带场景、时间、来源与已知后续变化，不能把过去的情绪当现在的状态。
- 长期记忆进入 Runtime Context，既不修改冻结角色提示词，也不把记忆中的自由文本当成优先级更高的系统规则。
- 提取到的持续事项交给其独立规则；保存提醒请求不等于已创建可投递的提醒。具体交接与失败反馈随后设计。
- 纠正/删除需影响引用旧内容的事实、经历、摘要与检索缓存。只给条目加来源 ID 不足以保证其他文本中的转述一并消失；细粒度追踪、失效与重建在生命周期分区具体收敛。

## 7. 当前代码需要对齐的点（只读发现）

1. `PersonalMemory` 当前只有一段正文、`fact/inference`、单个来源和 `active/deleted`；这不等于已经支持事实/经历分类、条件、时间与修订历史。新设计不能直接拿 `kind` 同时表示内容类别与证据性质。
2. 当前 `(instance_id, source_message_id)` 唯一，一条来源只能保存一条记忆；自动提取需要一条消息支持多条事实、多条消息支持一条经历。实施时需设计多来源关联，同时保留现有手动保存请求的幂等语义；不能简单移除唯一约束就认为问题解决。
3. 手动保存来源只接受同实例成功轮次的用户消息。共同经历可能引用角色发言，需要单独的内部证据契约；角色发言可证明其说过什么，不能用来确认用户的现实身份或外部行动。
4. 当前更正会增加修订号但不保存完整旧内容版本；新旧有效性、每次变化的依据需要补齐，不能把原始来源自动当作更正后内容的证据。
5. 当前删改会提高 `history_floor_revision`，排除实例所有会话中的旧历史，并保守清空状态/关系。这是现有防旧信息回流的边界。自动更新若直接高频复用该行为会影响连续性；实施自动写入前必须与摘要及生命周期契约对齐，不能悄悄取消保护，也不能声称现有代码已支持细粒度遗忘。

上述是后续实施前需要收敛的数据契约，不要求推翻现有聊天架构。本轮不修改表、迁移、接口、Provider、前端或运行数据。

## 8. 验收案例与本轮待评审建议

后续测试至少覆盖：一句话拆出多条独立事实；一条经历关联多轮；来源重放不重复；同名人物与跨实例隔离；临时例外不覆盖长期偏好；变化与纠错分别处理；历史叙述不覆盖当前事实；假设/游戏讨论不污染现实与 Canon；角色猜测不自动成为用户事实；尚未回应不算同意；纠正期间后台任务不能恢复旧内容；保存失败不宣称成功。

本轮补充：按原消息日期解释“昨天”，延迟重跑不改变日期；只知月份不伪造某日；跨年和未知时间不瞎补；旧事重提不改变发生时间；同事件跨批次/跨会话补充不重复；同日同人两件事不误合并；仅短聊未压缩也会整理；压缩与普通提取同时提交同来源不重复；崩溃重试不漏来源；来源不明确时不强行归并。

这是效果验收，除了存储与假 Provider 单元测试，还需设计成组对话样例检验语义提取。不能仅以 JSON 结构合法认定记忆正确。

本轮建议集中评审三项行为：明确且有长期价值的信息自动保存；第一版不自动固化人格推测；真实变化保留过去、纠正错误撤销旧结论。四项覆盖范围已经确认，这些具体默认行为尚未因为本次文档而自动获得批准。

验收参考：[LongMemEval](https://arxiv.org/abs/2410.10813) 将信息提取、多会话推理、时间推理、知识更新和依据不足时不作答列为五类长期记忆能力。本文据此补充测试维度；上面的条目组织与产品行为是 AfterStory 的设计建议，不是该论文保证有效的实现。
