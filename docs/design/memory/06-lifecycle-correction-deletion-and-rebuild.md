# 记忆生命周期：纠正、删除与重建

状态：2026-09-23 完整待审稿，未授权实现。本文定义权威数据、来源依赖、即时隔离和后台重建，解决旧信息通过摘要、事件、索引或排队任务重新进入上下文的问题。

## 1. 目标与基本原则

纠正和删除不是修改一段展示文本。相同信息可能出现在原消息、事实、经历、摘要、连续性笔记、状态/关系依据和检索索引中。系统必须先立即阻止旧内容继续进入模型，再异步重建受影响的派生材料。

推荐原则：

1. 原始成功消息、用户显式操作和当前有效结构化版本是权威依据；摘要、Embedding、检索索引和快照是可重建派生数据。
2. 每个派生项记录直接来源及生成版本；不能用“全文看起来无关”代替来源关系。
3. 纠正/删除提交时同步建立可见性屏障，后台重建没有完成也不会继续使用旧结果。
4. 无法证明某段派生文本不含目标信息时保守失效；不能为了连续性冒险泄漏已纠正/删除内容。
5. 保守失效造成的上下文缺口可以通过受控重建恢复，不自动恢复被禁止的信息。
6. 后台旧任务提交前必须重新核对实例修订、来源可见性和目标版本，防止旧内容复活。

## 2. 区分四种用户操作

| 操作 | 用户意图 | 推荐结果 |
| --- | --- | --- |
| 更新事实 | 情况确实发生变化 | 新版本成为当前事实，旧版本保留为过去状态及时间范围 |
| 纠正错误 | 以前记录或说法不正确 | 旧结论标记为错误，不再作为历史事实使用 |
| 删除保存的记忆 | 不再把该结构化条目用于角色记忆 | 条目退出召回；原聊天仍可浏览，相关派生项失效 |
| 忘记相关内容 | 不希望系统继续将某信息用于模型上下文 | 建立范围明确的抑制规则，排除来源及其派生内容；原聊天是否删除由独立操作决定 |

删除聊天记录是第五种独立数据操作：它删除或隐藏原始 Conversation/Turn/Message，并触发依赖失效。不能把“删除记忆”描述成聊天原文也已删除，也不能因为聊天仍可浏览就让已删除记忆重新进入模型。

V1 UI 可以先保留较少按钮，但确认文案必须说明实际范围。若只提供当前“删除记忆”，其语义至少要保证该信息不再从结构化记忆、摘要和自动提取回流；完整聊天删除可以后续设计，但内部生命周期需要预留。

## 3. 版本与状态

事实、经历、事项及其组件使用稳定实体 ID 和不可变修订。逻辑状态建议包括：

- `active`：当前可用于召回。
- `superseded`：真实变化后的旧版本，仅历史问题可用。
- `corrected`：已确认错误，不再作为真实历史使用。
- `deleted`：用户删除，普通和历史召回都不可用。
- `rebuilding`：权威内容仍存在，但相关派生表示暂不可用。
- `suppressed`：命中“忘记此信息”范围，不允许进入模型。

具体枚举可在实施契约中调整。关键是区分历史真实但过期、原本错误、用户删除和暂时待重建，不能都塞进一个 `inactive`。

新修订保存操作类型、直接依据、操作者、创建时间及它替代/纠正的版本。展示更新时间不能代替事实有效时间。

## 4. 来源与派生依赖

建议建立统一的来源引用/依赖边界，至少能表示：

```text
Message/Turn span
  ├─ Memory fact version
  ├─ Event component/version
  ├─ Ongoing matter revision
  ├─ Segment summary item
  ├─ Continuity note item
  └─ State/Relationship evidence

上述权威或派生内容
  ├─ Embedding/index document
  ├─ Runtime snapshot
  └─ Higher-level summary
```

来源需要多对多：一句话可以支持多个事实，多条消息可以支持一个事件。能可靠定位时记录消息内 span；无法定位时至少绑定整条消息。span 用于减少误伤，不用于声称自动理解百分之百可靠。

每个派生项记录生成器/模板版本、来源修订集合和内容散列。摘要引用摘要时仍保留最终原文依赖；不能形成只有摘要互相引用、无法追到原始依据的链。

## 5. 同步可见性屏障

纠正、删除或抑制先在一个有界短事务中建立运行时屏障：

1. 锁定实例和目标当前版本，检查 expected revision。
2. 写入新版本、墓碑或抑制规则。
3. 提高实例语义修订。
4. 写入目标实体/来源的不可用标记和可见性修订；来源关系不足时同步提高现有 `history_floor_revision` 等保守排除边界。
5. 登记持久化的依赖遍历、重建与清理任务；不在事务里遍历全部摘要、索引和关系依据。
6. 提交后让所有运行时读取按权威状态、来源依赖或保守边界过滤；无法核验来源的派生项暂不使用。

即时屏障依赖权威状态和查询硬过滤，不等待向量删除、摘要重写或缓存过期。读取不能只看派生表自身的旧 `active` 标志；必须核对其来源版本和屏障修订，无法完成核对时使用整段/整轮或实例级 floor 保守回退。正在生成的旧回复沿用现有 `context_revision` 检查并拒绝落库。已经发给外部 Provider 的请求无法撤回，但其结果不能被保存或继续产生有效派生写入。

显式操作成功响应表示屏障已经生效；后台重建可能仍在进行。界面可以显示“已不再用于回复，相关整理正在更新”，不能把异步清理中说成失败，也不能在屏障失败时说已经忘记。

## 6. 纠正与真实变化

### 6.1 真实变化

“我从杭州搬到上海了”创建当前居住地新版本，并关闭杭州版本的有效时间；旧版本仍可回答“以前住在哪里”。引用旧事实的当前状态、事项或摘要需要重新评估，但描述历史搬家经过的事件仍可保留。

### 6.2 纠正错误

“之前说错了，我一直住苏州”把杭州版本标为 corrected。它不能再回答用户曾经住杭州，也不能作为关系熟悉度依据。包含该结论的摘要与连续性笔记失效后，基于允许来源重建；无法安全重建则保持缺失。

### 6.3 含糊冲突

只有“我在上海”而无常住语义时，不自动进行上述任一操作。候选保持争议或等待澄清，当前回复避免声称已经搬家。冲突状态本身可以进入检索选择，但不能作为两个都确定的事实。

## 7. 删除、抑制与原始聊天

删除结构化记忆后：

- 普通召回、Embedding、全文索引和 Runtime Context 立即排除该条目。
- 直接基于它或重复其内容的摘要/事件组件进入失效或重建状态。
- 同一来源消息的其他独立信息只有在有足够细粒度来源时才可保留；否则运行时保守排除整条消息/轮次，原文仍可供用户浏览。
- 延迟提取任务不能从相同来源再次创建等价条目。

“忘记相关内容”比删除单条记忆范围更广，需要抑制目标。抑制目标可以来自明确实体/版本、来源消息范围和经用户确认的规范化主题；模糊语义不能自动扩展到所有相似私人内容。抑制规则本身只保存执行所需的最小识别信息和散列/引用，避免保留一份可直接召回的正文副本。

用户后来重新主动提供相同信息时，系统不能自行判断是否撤销抑制。需要明确询问是否重新记住，或按用户显式“重新记住”操作建立新依据。

## 8. 派生内容失效与重建

重建任务按依赖拓扑处理：

1. 遍历依赖关系，计算受影响的事实/事件/事项版本和来源范围；这一步在屏障提交后异步执行，不决定即时隔离是否生效。
2. 异步删除或禁用相应搜索索引与缓存键；清理前始终由已提交的权威屏障阻止运行时使用。
3. 重建分段摘要中的受影响条目；无关条目可复用。
4. 重算连续性笔记、当前事项视图和 Runtime snapshot。
5. 重新评估依赖这些内容的 State/Relationship 依据。
6. 为新的有效正文生成 Embedding/全文索引。

每一步使用持久化任务和幂等键，记录目标语义修订。任务读取固定允许来源，提交前确认实例仍处在兼容修订；过期任务丢弃结果并由新任务接管。失败时保持屏障，不回退使用旧派生项。

若来源消息包含被删除内容和无关内容，优先从 span/结构化来源重建；没有可靠 span 时不让模型阅读被禁止的完整消息来生成“干净摘要”。这种情况下牺牲部分连续性，直到用户重新提供或系统拥有安全来源。

## 9. 现有 history floor 的演进

当前实现中，个人记忆更正/删除会把 `history_floor_revision` 提升到新的 `context_revision`，从而排除该实例更早修订下的全部会话历史，并清空 State/Relationship。这是安全但粗粒度的屏障。

推荐迁移策略：

1. 第一阶段继续保留现有 floor，新增派生数据也必须遵守，先保证不会回流。
2. 建立多来源、版本依赖、抑制和重建覆盖后，使用细粒度可见性过滤恢复可证明无关的历史。
3. 只有测试证明所有运行时路径都经过新过滤，才能降低 floor 的主导作用；不直接删除旧保护。
4. 遇到旧数据没有来源 span 或依赖不完整时继续采用保守 floor/整轮排除。

这允许逐步提高连续性，不需要一次重构整个聊天架构，也不会为保留历史而先放松删除保护。

## 10. State、Relationship 与提醒联动

- State 快照引用被纠正/删除内容时立即失效；基于剩余有效近期事件重新计算或回到空状态。
- Relationship 的某个方面只移除受影响依据；若现有快照无法分解依据，先整体失效，再从有效关系事件重建。
- 删除提醒/事项会撤销未投递 occurrence；已经送达的投递记录可保留最小审计状态，但正文和运行时引用按删除范围清理。
- 关系变化不反向修改事实；事件被纠正后，只重新评估以它为依据的关系结论。

## 11. 用户可见状态与审计

用户至少能看到当前保存的事实/偏好、经历和持续事项，并执行更正、删除、完成或取消。历史版本和内部依赖不需要全部暴露，但界面应能说明来源类型、当前状态和“为什么角色记得这件事”的基本依据。

内部保留操作审计：request ID、目标、旧/新修订、来源、处理状态和错误码，不记录模型思维链。删除正文后的墓碑用于幂等与防复活；对用户可见的“已删除”不能通过普通 API 返回原正文。

## 12. 失败处理

- 屏障事务失败：操作整体失败，旧状态保持一致，不能回复完成。
- 重建失败：旧派生内容继续不可见，任务可重试；无关聊天可继续。
- 依赖图不完整：采用整段/整轮或 history floor 保守排除。
- 派生项数量很多：屏障事务只写有界权威状态与任务，不同步扫描整张依赖图；后台清理积压时硬过滤仍生效。
- 并发纠正：expected revision 保证一个胜者，失败方读取新版本后重试。
- 删除与后台提取并发：提交时的语义修订和抑制检查拒绝旧提取结果。
- 索引删除失败：权威查询硬过滤仍阻止命中；清理任务继续重试。

## 13. 当前代码对齐与验收

当前 `PersonalMemory` 只保存当前正文、单来源、修订号和删除墓碑；没有版本历史、多来源、span、抑制或派生依赖。当前 StateEvent 绑定一个成功 Turn，记忆变化会排除所有旧 StateEvent。新增设计需要演进这些边界，但保留现有实例锁、expected revision、request ID 和旧回复拒绝机制。

测试至少覆盖：真实变化可回答过去；纠错不保留错误历史；删除后所有检索路径立即不可见；旧摘要和 Embedding 不回流；排队任务不能复活；同消息多个事实只删除目标且缺 span 时保守排除；重建失败仍安全；跨实例不传播；并发纠正一个胜者；用户重新提供被抑制信息时不自动恢复；State/Relationship 只使用有效依据；旧数据回退到 history floor；数百个派生依赖下屏障事务仍有界。

用户审核重点：删除保存记忆和“忘记相关内容”的产品区别；可靠性不足时允许牺牲局部连续性的保守策略；底层墓碑与依赖审计保留范围；何时允许从粗粒度 history floor 切换到细粒度重建。
