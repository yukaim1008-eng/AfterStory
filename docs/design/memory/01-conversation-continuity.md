# 长会话连续性与上下文压缩

状态：2026-09-18 设计讨论稿，尚未确认详细方案，未授权实现。本文只设计 Memory System 的长会话连续性分区；角色 Schema、完整长期记忆提取、关系变化、提醒调度与通知分别维护。

## 1. 目标、已有约束与当前缺口

已确认目标：同一角色实例可以持续交流，不因超过最近 12 轮或切换会话就失去所有早期脉络；支持压缩上下文，并为后续长期记忆提供接口。线上提醒先做、离线通知留到后续工具编排，见 [记忆分区](../03-memory-state.md)。

沿用 [V1 基线](../../decisions/0001-v1-baseline.md)：用户/角色/实例隔离；Canon 与个人经历分开；短期状态与长期关系分开；事实与推测分开；可纠正删除；不伪造经历或保存模型思维链。

代码现状：

- `ContextAssembler._history` 读取当前会话最近 12 个成功轮次，可配置；无 token 预算、摘要、覆盖范围或历史检索。
- 个人记忆按更新时间读取，最多 20 条/6000 字符；它不是相关度召回，也不是对话摘要。
- `begin_turn` 在会话与实例行锁事务中调用 `ContextAssembler.build`，之后才提交事务并调用文本 Provider。
- 记忆修改/删除会提高 `history_floor_revision`，该实例所有会话中更早修订的原文不再进入上下文；原文仍可浏览。生成中的旧修订回复也不能提交。
- 模型配置有输出 `max_tokens` 与超时，无输入预算或上下文窗口字段；不能把输出上限当成模型窗口容量。

本方案追求：重要内容和未完交流可靠连续，旧细节可查证，每次请求有明确容量上限。不能承诺任何长度下逐字记得全部历史；保存原文也不等于每次都能正确检索到它。

## 2. 建议采用的四层表示

以下均为建议。四层是数据表示和读取职责，不意味着四个独立服务。

| 层 | 保存内容 | 何时进入模型 | 约束 |
| --- | --- | --- | --- |
| 原始记录 | 原始消息、说话方、轮次、时间、会话与实例引用 | 最近原文或被定向召回的片段 | 压缩不删除原文；保留的是谁说过什么，不自动证明内容真实 |
| 分段摘要 | 一段已完成对话的主题、经过、变化、结论与来源 | 最近已压缩部分或与本轮有关的旧片段 | 从原文生成，带覆盖范围；已发布版本固定，纠错以新版本替换 |
| 连续性笔记 | 当前话题、指代对象、未回答问题、有效局部约定、尚未收束的互动 | 与当前交流有关的小部分 | 有来源、状态、时间与容量约束，不是长期用户画像，也不替代 State/Relationship |
| 本轮上下文 | 角色提示词、有效记忆/状态、选中摘要与证据、连续性笔记、近期原文、当前输入 | 本轮 Provider 请求 | 运行时按预算组装；不把整段完整提示词持久化 |

分段摘要积累后，可建立小型话题/时间概览以便定位分段。概览必须指向原摘要和原文；不是将唯一总摘要无限递归重写。仅在规模需要时增加层级，不先建设复杂摘要树。

压缩覆盖与上下文选择分开：历史可以全部完成归档整理，但某一轮只选其中相关部分。不能通过把所有分段摘要逐一加入请求，让上下文重新无限增长。

## 3. 摘要应保留什么

建议采用受约束的语义分区，而不是要求模型自由写一篇故事。具体序列化字段以后确定。

| 内容 | 保留要求 | 容易出现的错误 |
| --- | --- | --- |
| 话题与指代 | 人物、物件、方案等主体；“第二个方案”究竟是什么 | 只有“讨论了计划”，后续无法理解指代 |
| 陈述及来源 | 用户明确说过什么、角色说过什么、谁在转述谁 | 把角色猜测、引用文本或假设当成用户事实 |
| 决定及变化 | 已确认、拒绝、取消、替代、仍未确定 | 把建议写成已采纳，把计划写成已经发生 |
| 未完事项 | 尚未回答的问题、双方明确的局部约定、下一步 | 问题一被压缩就消失，或已经完成仍反复追问 |
| 互动经过 | 可观察的情绪表达、触发原因、道歉及对方回应 | 自行计算信任变化，或把某次情绪固化成性格 |
| 精确片段 | 与当前约定有关的日期、数值、名称、少量关键原话及消息引用 | 从摘要伪造“你当时原话是……” |

“用户说受到忽视，角色已道歉，用户尚未回应道歉”是交流记录；“角色信任降低”是状态/关系策略，本分区不生成后者。长时间间隔后，这段记录仍是当时发生的事，不能直接认定双方现在仍处于同样情绪。

常规寒暄、重复解释和无新信息的确认可以收缩；玩笑、昵称或一句承诺若对后续指代/互动有作用，则保留必要片段。旧细节不全靠摘要保存，允许后续查原文。

压缩摘要是派生材料，不获得系统指令权限。角色规则保持独立；用户历史中的“忽略规则”等内容即使进入摘要，仍只能作为被记录的话语。来源、隔离与过滤应由代码保证，不能只依赖一句提示词。

## 4. 何时压缩与如何分段

### 4.1 先定义输入预算

建议每个模型配置可用窗口和应用输入预算，计算：

`本轮输入上限 = min(应用输入预算, 模型可用窗口 - 输出预留 - 安全余量)`

计入角色提示词、所有数据块、消息包装、当前输入等完整请求。计数器应匹配实际模型；没有精确计数能力时使用保守估算与实测 usage 校准，不声称字符数就是 token 数。

示例仅解释预算，不是选定参数：若本轮输入预算为 16,000 token，可暂以角色及固定背景 2,000、有效记忆/状态/召回材料 3,000、摘要与连续性笔记 2,000、近期原文 8,000、当前输入 1,000 分配。各项按实际长度动态借用余量；输出与安全余量在此之外预留，不能把这些配额都当成必须填满的目标。

压缩主要作用于增长的对话部分；超长用户输入、召回材料或静态提示词也必须独立检查，不能指望压缩历史解决所有超限。

### 4.2 建议双阈值

- 软阈值：已完成对话逐渐接近预算时，提前对较早部分准备摘要。可以比较输入预算占用 70%–80% 等候选值，尚未确定。
- 回落目标：完成压缩后应明显低于软阈值，避免每新增一条消息就再次压缩；具体余量通过对话回放测量。
- 硬上限：发送请求前检查全部上下文；未满足上限不调用回答模型。

压缩边界尽量靠近话题结束，并以完整成功轮次为单位。模型不能决定无限延后分段；达到块容量上限时仍需切段，通过连续性笔记和来源引用承接未结束的话题。

近期原文保留完整连续后缀。可设置少量完整轮次的优先保留目标，但它服从硬预算；不恢复成“超过固定轮数直接丢弃”。单轮超长需要单独缩减材料或提示用户分段，不能截断半句冒充原文。

## 5. 压缩后的接续与历史找回

建议本轮上下文的逻辑组成：冻结角色提示词 → 实例有效记忆及 State/Relationship → 选中历史材料、摘要与连续性笔记 → 近期完整原文 → 当前用户输入。新增块的相对位置需要实际回放评估；延续角色规则和当前输入的明确边界。

每次先读取当前输入和近期原文，判断需要哪些背景，再在预算内选择：

1. 当前仍生效的局部约定和指代，如用户刚明确“先听我说完，不用给建议”。
2. 保证最近压缩点前后衔接的摘要与未完问题。
3. 与本轮有关的旧话题/事件，以及后续长期记忆模块提供的候选。
4. 若用户询问准确日期、原话或追问摘要未保留的细节，回读来源原文。

第一版也需要受权限约束的原文读取与历史查找入口，不能只预留一个空召回接口后声称完整长期连续。候选路径可以结合消息引用、时间、人物、关键词和后续语义检索；不能以“摘要里没写”断言历史里从未提及。Embedding 与精排选择留在召回分区，但本分区的验收必须包含压缩后细节找回。

查原文应是应用内部读取流程，不依赖未来外部 Tools 编排。回读片段包含必要的邻近发言和已知后续纠正，避免脱离否定、转折或改期语境；只有原文支持时才能逐字引用，摘要只能支持复述大意。读取范围、返回字数和尝试次数有上限；仍找不到、来源已不允许使用或有歧义时，自然表达不确定并澄清，不伪造精确记忆。系统保留内部来源引用，日常角色对话不需要每次展示技术标识。

示例：前段用户讨论 A/B/C 三个方案，确认 B；后段说“刚才第二个还是算了”。连续性笔记应指出 B 是哪个方案、当前状态；必要时取回候选方案原文，再更新本轮理解。不能只凭摘要“讨论并确定过一个方案”回答。

### 跨会话连续性

技术上的新 Conversation 不等于新 CharacterInstance。相同实例可以选择与当前问题相关的其他会话摘要、有效记忆和未完线索；不要把其他会话的最后几句机械拼成本会话刚发生的话。

摘要归具体会话，读取权限与运行数据归实例；跨会话材料保留会话来源、真实时间或“时间未知”。`Turn.sequence` 只在当前会话唯一，不能将其他会话的相同序号当成同一轮，也不能用它排序跨会话时间。不跨实例合并，同名角色和用户也不能绕过此边界。

未完成的话题可以暂搁，不能因为尚未关闭就每轮催问。当前工作集只放相关线索，其余保留可查索引；移出工作集不等于事项已经结束。

## 6. 避免反复摘要后失真

- 分段摘要直接基于其覆盖的原文；可以读取少量边界前文用于理解，但边界前文不再计作新覆盖或新事件。
- 后续概览引用固定分段及版本。新输入加入后增量更新相关部分；不将上一次总摘要当成唯一证据。
- 连续性笔记可以更新，但保留条目来源及替代/关闭依据。重要更新重新核对来源；不能因为上次笔记写过，就当成事实已被再次证实。
- 同一来源在摘要、笔记和召回结果中去重；必要的主题概览不应把同一事实反复堆入上下文，重复出现也不能提高可信度。
- 摘要输出检查覆盖范围、来源 ID、结构、长度、关键数值/原话匹配及冲突。格式合法不等于语义正确；需要回放抽查，不能承诺校验器能识别所有语义丢失。
- 无新信息的分段可以标记“仅寒暄/无新增事项”，但仍记录处理范围，不伪造重要记忆来填满配额。

为每个摘要记录概念上的来源消息/轮次、所属实例与会话、来源修订、摘要器/模板版本、已验证状态。此处定义需要的信息，不在本轮决定表结构或 migration。

## 7. 可靠性与现有实现的接入边界

### 7.1 提前准备，发布后才替换

建议默认在成功轮次完成后，达到软阈值时创建可重试的摘要任务。任务读取固定来源快照，在数据库事务之外调用模型；结果检查完成后，短事务确认来源及修订仍有效，再原子发布摘要和处理范围。

原文近期窗口不能因任务已排队就提前消失。每个符合当前修订的成功轮次，要么仍由未压缩原文承接，要么已被有效分段覆盖；失败轮、处理中轮次不能推进摘要覆盖。来源清单要核对实际成功轮次 ID，不能假设一个 sequence 区间内全部成功；重试同一轮也不是新经历。更正/删除明确排除的范围不属于待补压缩内容。

归档完整不等于全部摘要每轮注入：完整覆盖用于发现遗漏和回溯，实际请求依然只选择预算内相关内容。

### 7.2 故障与容量冲突

- 摘要失败且原上下文仍能放下：继续使用原文，保留任务以便重试；不阻塞每轮聊天。
- 即将超过硬预算且没有有效摘要：建议显示简短等待状态，受限等待/补做压缩；超时保留用户输入并允许重试。
- 默认不把“删掉最旧一段、假装没发生”作为无提示降级；若用户更重视延迟，可讨论显式降级模式。
- 检索失败且本题依赖历史细节：不能把失败当成“从未发生”；说明暂时无法确认。与历史无关的交流可继续。
- 核心角色提示词和当前输入本身已超限：明确返回可处理错误或请用户分段，不能无限压缩其他内容。
- 服务重启后未完成摘要任务可恢复，重复执行不产生重复分段；记录处理范围和版本。用户关页面不应成为提交摘要的必要条件。

已有长聊天的首次接入需要分批补摘要，不能假设过去已全部压缩，也不能一次调用塞入全部历史。正在补做时，对覆盖不足又无法放入预算的请求采用同样的等待/重试策略；补做不包括已经被删改边界排除的历史。

### 7.3 成本控制

按新增来源范围增量处理，不每轮重读全部原文或全部摘要；新分段摘要与连续性笔记的更新尽量在一次有结构的处理里产出。日常只做有界选择，需要准确旧细节时才扩展读取。摘要本身也有独立输入、输出和超时预算。

后台任务不会消除模型费用，只把部分延迟移出发送链路。摘要调用频率、累计 token 和积压需要测量；模型选择依据事实保留与语义错误率比较，不能仅因摘要“看起来简单”就默认选择最便宜模型。具体模型与预算后续确定。

### 7.4 锁、修订与 lease

`ContextAssembler.build` 当前在 `Repository.begin_turn` 的行锁事务内调用。本方案不允许在其中加入摘要或检索模型请求。长耗时准备应在事务外完成，再在预留轮次时核验快照，事务内仅做有界数据读取与组装。

现有 `context_revision` 是运行数据语义变化与旧回复失效边界；摘要版本应有独立版本标识，不能每次纯压缩发布就提高实例语义修订、让正在生成的回复连续失败。记忆更正/删除等实际语义变化仍沿用现有拒绝旧回复的机制。

补做摘要与回答模型的总耗时要与轮次 lease 一起设计，不能把两个模型调用简单串进现有 120 秒租约。小范围调整编排边界即可，不以此引入 LangGraph 或重构 Provider。

另有已核查的性能事项：`begin_turn` 当前每轮加载本会话全部 Turn，历史越长读取越多。未来实现长期连续性时应对请求幂等、处理中轮次、最新轮次做有界查询并回归原并发语义；本轮只记录，不修改。

## 8. 纠正/删除：必须明确的连续性取舍

已实现的 F2 保护是实例级粗粒度排除：一次个人记忆修改/删除会排除更早修订的所有历史，并清理旧状态的可用性。这个机制阻止被排除的旧轮次再次通过现有历史上下文进入模型，但会牺牲与纠正无关的对话连续性。它不是内容级全局遗忘：其他有效记忆中的重复内容、用户后来重新输入的信息并未被这道历史过滤自动处理。

本方案建议分清两层：

1. 首次接入压缩必须继承现有排除边界。摘要、连续性笔记、概览、检索索引及原文回读都不能绕过；后台旧任务也不能重新发布已经失效的内容。原文可浏览不等于可重新送入模型。
2. 为达到长期陪伴的完整体验，后续记忆生命周期设计需要收敛来源追踪和受控重建：隔离受影响事实及其派生材料，保留可证明无关的背景。不能只以“摘要来源未包含那条 memory ID”判断安全，因为信息也可能出现在旧对话和角色回复中。无法可靠判断时保守排除。

第 2 层尚未确认实现算法，是整体 Memory System 验收前必须解决或明确接受的限制；不能把仅完成压缩说成所有长期记忆问题都解决。也不能从禁止读取的旧原文直接生成“新修订摘要”绕过删除。

## 9. 与其他 Memory 分区的接口

- 长期记忆：压缩可以提供带来源的候选和历史索引，但不在这里确定自动提取/写入规则。长期记忆处理未完成时，原始证据和分段来源仍保留，不要求一定先写入 `personal_memories` 才能压缩。
- 持续事项/线上提醒：记录“讨论过某计划、尚未完成”的对话线索；正式事项的时间、改期、取消、已提醒状态仍由对应分区负责。压缩不能自行创建提醒或执行承诺。
- State/Relationship：消费已有有效快照，摘要只保存可观察的交流经过，不自动覆盖快照或推断关系升级。
- Character/Canon：使用实例绑定的版本；历史陈述不升级 Canon，不改写冻结的角色提示词。

## 10. 验收设计

以下是设计用例，不是已经运行的测试。工程正确性和模型摘要质量分别验收；fake Provider 能验证前者，不能证明后者。真实模型回放在实施阶段另行确定供应商、样本与调用预算，本轮不调用模型。

| 场景 | 预期行为 |
| --- | --- |
| 长消息与大量短消息混合，连续跨越至少 3 次压缩边界 | 最终请求均在预算内；无未处理原文被静默跳过；处理范围无重复归档 |
| 早期三个方案，中途选 B，压缩后用户说“第二个取消” | 识别第二个的具体内容；保留选择与取消先后，不继续视为有效计划 |
| “假如我换工作”“不是离职，只是请假”，夹杂玩笑和引用 | 保留假设与否定，不写成已离职事实 |
| 用户说受委屈，角色道歉，后续尚未回应；之后隔几天继续 | 压缩不抹掉未收束互动，也不伪造和解或断定当前仍在生气 |
| 用户要求复述数百轮前的短句/具体日期，摘要未保留原话 | 定向查有效原文，准确引用；无法确认时不编造 |
| 相同实例新会话追问旧话题，另一个用户/角色/实例有相似内容 | 能取正确来源并区分历史时间，绝不跨实例读取 |
| 摘要任务运行时用户更正/删除；服务重启或重试 | 旧任务不能发布失效内容，原文/摘要/索引不重新带回已排除信息 |
| 摘要超时、输出非法或截断；新输入突然很长 | 不提前丢原文；触发有界等待/可重试错误，不发送超限请求 |
| 大量旧摘要，只有一个旧话题与本轮相关 | 不全量拼接摘要；按需选择并能下钻原文；无依据时保留不确定性 |

比较基准建议包含：现有最近 12 轮、单份滚动摘要、本方案分段＋连续性笔记＋原文回读。同一批带人工预期的对话测关键事实/否定/决定/未完事项保留率、压缩边界前后接话质量、错误回忆、准确引用、删除失效，以及 token、延迟、后台摘要积压。先建立基线再定质量阈值，不预先声称召回达到某个百分比。

## 11. 本轮集中评审的产品取舍

| 取舍 | 建议 | 影响 |
| --- | --- | --- |
| 原文是否因压缩被清理 | 保留，删除遵循另行确定的用户管理规则 | 能查证细节和重建摘要，存储随历史增长 |
| 压缩表示 | 分段摘要＋小型连续性笔记＋近期原文 | 比单份总摘要多维护来源，但更容易查错与接续 |
| 容量冲突时的行为 | 平时提前压缩；硬上限时宁可短暂等待/可重试失败，也不无提示截断 | 大部分轮次无额外等待，少数轮次可能更慢 |
| 找回旧细节 | 提供有界的历史查找与原文回读 | 记忆更可靠；涉及远期细节的回复可能增加耗时 |
| 更正/删除后的连续性 | 先遵守现有边界，完整 Memory 设计补来源追踪与受控重建 | 压缩可单独实施，但暂不能承诺纠正后完全不断片 |

确认这些方向后，再细化摘要样例、预算与触发参数、候选数据契约和一个有边界的实施阶段。用户确认方向不自动构成开发授权。

## 12. 参考与适用范围

- [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：讨论压缩、持久笔记与按需取上下文。本文借鉴这些思路，具体陪伴场景取舍为本项目建议，不照搬编码 Agent 工作流。
- [Lost in the Middle](https://arxiv.org/abs/2307.03172)：在研究所测模型和任务中发现长上下文信息位置会影响利用效果；提示我们应实测有效上下文，而不是只看宣称窗口，不能外推当前模型的固定容量或性能。
- [LongMemEval](https://arxiv.org/abs/2410.10813)：覆盖信息提取、跨会话与时间推理、知识更新和无法回答时的表现，为验收维度提供参考，不代表本项目已经达到对应分数。
