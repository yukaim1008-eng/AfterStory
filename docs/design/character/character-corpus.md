# 人物资料研究库：最合理实施顺序

状态：M0 已完成；M1 已登记第一套 B 站完整剧情来源，等待字幕提取试跑。

## 目标与边界

研究库用于保存可追溯的游戏档案、剧情场景、人物表现证据和人物特征归纳。它服务于当前三位主角色，也允许在同一段剧情中顺带积累其他命名角色的资料。

研究库不属于用户 × 角色实例运行数据，不进入 Memory、State 或 Relationship；未经审核的研究结果不进入 `CharacterVersion.definition`，也不直接展示在 Web。

## M0：目录、来源和个人档案

1. 建立角色稳定 ID 与中、日、韩、英名称目录。
2. 建立来源记录，保存平台、页面、revision、采集时间和内容哈希。
3. 同步异环信息站中从游戏个人档案搬运的结构化资料。
4. 完整页面保存在本地可重建缓存；Git 只保存事实索引、档案标题和语音覆盖统计。
5. 建立 SQLite 查询库，并验证唯一键和跨文件引用。

当前结果是 24 名角色、24 条来源记录和 23 份已采集个人档案。查询库从 23 个页面中识别出 143 个档案条目与 1955 条语音；明音凛页面当前缺失，保持 `discovered`。

## M1：B 站剧情来源清单

1. 用户提供候选视频或系列入口。
2. 优先选择完整、无跳过、字幕清楚、版本和章节明确的录屏。
3. 以 BV 号、分 P、游戏版本和内容类型去重。
4. 先记录覆盖范围，不立即生成性格结论。
5. 原始视频不进入 Git；来源 URL 和时间定位可以提交。

用户只需要提供 B 站视频或合集链接；剧情类型、版本和完整性说明属于可选信息。Agent 先完成去重和覆盖审查，再列出确实缺失、需要本地录屏或补充定位的部分，不要求用户预先手工整理每一集。

当前已登记 `BV1kqoaBiEVZ`：标题为《异环》主线及番外剧情纯享，男主中配，标注更新至 1.4；共 21 个分 P、80,387 秒，包含第 0–8 话和三个番外。分 P 标题和时长结构清楚，适合作为剧情覆盖主来源。B站接口未提供 CC 字幕或章节标记，但用户确认录制的游戏画面内含字幕；下一步先从一个分 P 截取 3～5 分钟，校准字幕区域、逐字显示完成时机、说话者区域和 OCR 准确率，再处理完整分 P。

## M2：场景化整理

1. 每个视频按语境拆成场景，保存起止时间、章节和摘要。
2. 同一场景登记全部命名参与者；无名路人只留在上下文。
3. 字幕可访问时使用字幕；只有画面字幕时，使用本地视频的字幕区域 OCR。
4. 每段剧情只处理一次，不为不同角色重复转录。
5. 场景绑定 `canon_checkpoint`，避免未来把后期认知写入早期版本。

## M3：人物表现证据

1. 从场景中分别提取各角色的选择、反应、表达方式和关系表现。
2. 区分直接观察、较强归纳和暂定判断。
3. 每条证据记录适用范围和不能推出的结论。
4. 用户确认的角色理解可以先标为 `provisional`，之后补剧情证据。
5. 玩家评论只用于发现线索，不单独升级为稳定性格。

## M4：人物特征卡

1. 将多条场景证据合并为稳定、辅助或条件性特征。
2. 每个特征记录触发条件、可观察表现、频率和反向边界。
3. 对相互有张力的特征共同建模，例如伊洛伊的温和与顽劣。
4. 当前优先完成娜娜莉、伊洛伊、薄荷；其他角色保持证据积累状态。
5. 用户集中审核后，特征才进入 `evidence_confirmed` 或 `user_confirmed`。

## M5：生成产品资料

1. 从已审核特征压缩生成六字段 Character Definition。
2. 建立新的不可变 `CharacterVersion`，由 Prompt Builder 编译 Prompt。
3. Web 只读取审核后的简介、特征和关系资料，不展示内部推断过程。
4. 旧实例不自动升级；新版本先以独立实例进行实际聊天测试。
5. 完整 Canon、Voice 和剧情资料展示仍按后续独立阶段推进。

## 本轮停止点

M0 已具备可重复同步、验证和建库能力，M1 已完成第一套合集的来源与分 P 索引。下一阶段只对一个短分 P 做字幕提取与场景化试跑；在没有可核对的剧情文本前不生成 Traits，也不直接处理整套 22 小时录像。
