## 职责与已确认约束

负责 Personal Memory、Character State 与 Relationship。完整规则引用基线 5.1、5.2 节，十二项相处、记忆与回复规则已全部采纳。

记忆有选择、区分事实与推测、支持纠正和删除；短期情绪与长期关系分开；内部关系采用熟悉、信任、亲近并保留依据；用户不看到关系评分。

## F2 阶段 B 已实现

- 用户可以手动填写个人信息，也可以从同一角色实例、已完成轮次中的用户消息保存；系统不自动提取。
- 当前只产生用户确认的 `fact`，保留 `inference` 类型边界供未来明确的提取流程使用，不伪造推测记录。
- 创建请求 ID 幂等；同一来源不会重复保存。纠正和删除要求预期修订号，同一实例写入使用数据库行锁串行化。
- 删除会清空记忆正文并保留墓碑、原内容散列和来源标识，避免重试或同一来源使内容复活；原始聊天不会被删除。
- 纠正或删除推进实例上下文修订边界，供阶段 C 排除可能含有旧信息的历史上下文。
- 前端支持列表、空白、错误、添加、更正、删除确认和来源跳转，并明确内容由用户主动保存。

接口为 `GET/POST /instances/{instance_id}/memories`、`PATCH/DELETE /memories/{memory_id}`，同时提供 `/api` 前缀。`GET /health` 中 `memory=true` 表示手动管理可用，`memory_extraction=false` 表示没有自动提取。

## 后续设计

阶段 C 已接通个人记忆的有限上下文读取；阶段 D 已建立以下内部边界：

- Character State 保存可空的短期交流状态描述；Relationship 分开保存熟悉、信任、亲近三个可空文字描述，不使用好感度分值。
- 内部状态提交必须绑定同一实例的成功轮次，使用请求 ID 幂等、预期修订号和实例行锁，并将事件依据与两类当前快照原子保存。
- 普通聊天不自动提交状态。当前没有状态变化算法，也没有面向用户的状态、关系或评分 API。
- 有效状态以明确的数据块进入上下文。状态提交会推进实例上下文修订，生成中的旧回复不会写入。
- 个人记忆更正或删除会保守清空当前状态/关系并排除旧状态事件；旧事件仍保留为内部依据，但不会再次进入上下文。修订边界前的轮次不能重新提交状态，以免带回已纠正内容。

完成这些存储边界不等于采纳自动提取、Embedding、权重、衰减或状态变化算法。当前不以补全角色性格与资料库为前置任务。

2026-09-18 用户确认 Character Schema 暂按身份、性格、说话方式、行为、世界观、初始关系六部分拆分，见 [角色系统](01-character-system.md)。Memory System 设计沿用稳定定义与实例运行数据的隔离边界；等 Memory System 完成后再根据实际接口优化角色结构与内容，不要求当前先补全完整角色定义。

- 提取、检索、纠正、删除及来源关联的数据契约。
- 三个关系方面的自动变化检查和情绪缓和机制。
- 重试幂等、跨实例隔离，以及删除后避免旧上下文重新引入信息的处理。
- Embedding Provider 与 pgvector 接入方式。
