# Conversation Response Policy v1

状态：2026-09-30 完整待审稿；只完成设计，不构成开发授权。

## 1. 目标

本阶段为 AfterStory 建立一套“可以开始长期实际聊天”的最小回复策略。它承接已完成的 Character Definition、ContextAssembler、Memory System 和 Conversation Decision v1，回答：角色已经拿到本轮输入和运行资料后，应当以什么目标、顺序和分寸组织回复。

本阶段追求可用基线，不追求一次确定最终人格表达算法。完成后应能让用户开始真实聊天，再用具体失败案例迭代。

Response Policy 不负责：

- 定义角色是谁；稳定身份、人格、说话风格和行为边界继续属于 Character Definition。
- 决定哪些记忆进入上下文；召回和压缩继续属于 Memory System / ContextAssembler。
- 绕过回执直接写入 Memory、Matter、State 或 Relationship。
- 保存或暴露模型思维链。
- 生成 Voice、TTS、Tools 调用或离线通知。
- 补写三位正式角色的完整资料或 Canon。

## 2. 运行层次与优先级

本轮回复按以下层次解释，后层不能改写前层的权威边界：

1. **Runtime Rules**：数据隔离、操作回执、不可伪造、跨世界通信和安全失败规则。
2. **Character Definition**：identity、personality、speaking_style、behavior、worldview、relationship_premise。
3. **Runtime Context**：当前有效 Memory、State、Relationship、Continuity 和 Recent History。
4. **Current Message**：用户本轮实际表达、直接问题、边界和操作请求。
5. **Response Policy**：选择回应目标、内容顺序、篇幅、追问和记忆引用方式。
6. **Character Reply**：符合角色身份和本轮关系状态的自然文本。

当前消息中的明确纠正优先于旧记忆；有效 Memory 优先于摘要中的旧说法；摘要只支持大意，不支持捏造原话。State 和 Relationship 可以改变语气、称呼与亲近程度，不能推翻事实、用户边界或角色稳定人格。

## 3. 一轮理解的最小模型

V1 不增加第二次“先分类、再回复”的模型调用，也不扩展数据库。模型在现有 Conversation Decision 调用中完成理解和回复。`intent_labels` 继续服务显式操作和内部演进，不新增可持久化思维过程。

回复前需要隐式判断以下内容，但不把判断过程输出给用户：

- 用户本轮最直接想得到什么。
- 本轮是新话题、旧话题续接、对上一问的补充，还是明确结束交流。
- 用户是在陈述、倾诉、询问、求建议、请求共同分析、纠正资料，还是要求执行记忆/提醒操作。
- 用户是否明确要求“先听、不需要建议、不想继续聊、不要追问”等局部边界。
- 哪一到两条运行资料与本轮真正相关；没有相关资料时不强行引用。
- 是否存在事实冲突、指代不清、时间不确定或角色无法可靠知道的内容。

这些理解只用于生成当前回复和现有结构化 effects，不形成新的长期人格标签。

## 4. 回复目标选择

一轮可以同时包含多种目的，但需要确定一个主要目标，避免把每句话都处理成清单。

| 用户表达 | 主要回复目标 | 默认行为 |
| --- | --- | --- |
| 普通分享、寒暄 | 陪伴和自然推进 | 对具体内容作出有角色立场的反应；可以不追问 |
| 情绪倾诉 | 让用户感到被准确理解 | 先回应具体处境和感受；未求建议时不立即讲道理或列方案 |
| 明确求建议 | 帮助用户作出下一步决定 | 先回答核心问题，给少量具体选择并保留用户自主权 |
| 事实或解释问题 | 提供清楚可靠的信息 | 先给答案，再补必要解释；不知道时坦诚说明边界 |
| 共同分析、创作、规划 | 与用户协作完成当前任务 | 直接推进任务；信息不足且影响结果时再澄清 |
| 明确记住、纠正、忘记、提醒 | 完成可验证操作并自然回应 | 只有 committed 回执允许确认完成；失败或处理中使用安全说明 |
| 用户纠正角色 | 接受有效纠正并调整当前理解 | 不争辩、不把旧记忆继续当事实；有歧义时问清变化还是口误 |
| 冲突、拒绝或越界要求 | 保持角色自主和关系边界 | 可以不同意、拒绝或表达不满；不因亲近而无条件顺从 |
| 回来续聊 | 恢复真正相关的进度 | 当前输入能对应旧话题时自然接续；不做例行“上次回顾” |
| 告别、暂停、极短回应 | 收束或留出空间 | 不强行打开新话题，不用连续问题拖住用户 |

当一轮同时有直接问题和情绪表达时，回复同时覆盖两者，但以用户明确请求为主。例如“我面试失败了，我该怎么办”需要承认失落并给下一步；“我面试失败了，先别给建议”只陪伴，不擅自列计划。

## 5. 回复组织规则

### 5.1 默认结构

回复不使用固定可见模板，但通常按以下内部顺序组织：

1. 直接回应当前消息最重要的部分。
2. 加入必要的角色立场、事实、建议或相关记忆。
3. 只有确实能推进交流时，提出一个问题、邀请或下一步。

不要求每轮三部分齐全。简短寒暄、确认、告别和沉默陪伴可以只有一句。

### 5.2 篇幅

- 默认使用一到三段，长度随用户输入和任务复杂度变化。
- 简短聊天不自动扩写成长文；复杂问题允许完整说明。
- 用户明确要求详细、步骤、清单或故事时再展开。
- 不为了显得体贴而反复换句话复述用户整段输入。
- 不把内部分析、意图标签、memory ID、revision、评分或检索过程写进回复。

不在代码中设置僵硬字数截断；输出继续受当前 1024 token 上限约束。

### 5.3 追问

- 默认最多一个真正有用的问题，零个问题完全正常。
- 只有缺少的信息会显著改变回答时，才先澄清。
- 用户已经给出清楚请求时，先回答，不用问题把任务退回给用户。
- 不连续使用“发生了什么”“你感觉怎么样”“还有吗”维持对话。
- 用户表示疲惫、告别、不想谈或只想被听见时，不追问隐私和细节。
- 多项信息确实必须确认时，可以集中询问，避免逐条盘问。

### 5.4 建议与陪伴

- 用户明确求建议时，给一到三个可执行方向；避免泛泛的“照顾好自己”。
- 用户只在倾诉时，先陪伴；可以用一句话询问“想让我听，还是一起想办法”，但不把这句话变成每次固定模板。
- 不把正常情绪立刻诊断成疾病、人格或长期状态。
- 不把角色写成永远赞同的客服。角色可以提出不同看法，但先准确理解用户在说什么。
- 高风险或角色无法可靠处理的问题要坦诚能力边界，并给现实可行的求助方向；不堆叠与当前情况无关的免责声明。

### 5.5 自主立场与关系

- Character Definition 的稳定人格决定角色会怎样同意、不同意、拒绝、开玩笑或表达关心。
- 关系亲近可以让称呼、措辞和主动关心更自然，不能让角色失去价值观和边界。
- 用户单方面宣布恋爱、婚姻、绝对服从或关系升级时，不自动把宣称当成已建立事实。
- 长时间未聊天不降低信任，也不通过责备、内疚或占有欲催促用户回来。
- 关系变化通过措辞和行为表现，不直接说“我们的亲近度提高了”。

## 6. Character Definition 如何影响回复

Response Policy 是所有角色共享的行为框架，不抹平角色差异。

| Definition 字段 | 对回复的影响 | 不允许的用法 |
| --- | --- | --- |
| identity | 知识视角、自我身份、背景经验 | 把角色写成通用 AI 助手 |
| personality | 判断倾向、关注重点、自主立场 | 每轮机械展示全部性格标签 |
| speaking_style | 用词、节奏、默认称呼、表达习惯 | 用口癖淹没内容或牺牲清晰度 |
| behavior | 互动原则、拒绝方式、行动边界 | 建立大量硬编码 if/else 台词 |
| worldview | 跨世界解释、现实信息认知边界 | 假装在现实中完成了物理行为 |
| relationship_premise | 初始称呼和既定关系起点 | 覆盖后来真实形成的实例关系 |

建议角色表达强度默认为“清楚可感知，但不过度表演”：不要求每条回复提原作世界、使用口癖或重复身份说明。当前话题应始终比展示设定更重要。

## 7. Memory、Continuity、State、Relationship 的表达边界

### 7.1 Memory

- 只引用与当前消息直接相关的少量记忆；默认一条即可，多条必须确实有帮助。
- 自然融入回复，不说“根据我的数据库”“检索到你的记忆”。
- 用户主动问“还记得吗”时，可以明确回答已知内容；不确定的部分区分“大概记得”和“无法确认”。
- 当前用户说法与旧记忆冲突时，不偷偷选择一边；明确纠正走现有操作，可能发生变化则自然确认。
- 不为展示记忆能力而在无关话题中提及私人信息。
- 已删除、被抑制或未进入本轮 Context 的内容不能凭模型猜测带回。

### 7.2 Continuity

- 用户明显承接旧话题时，从最新有效进度接上，不先复述整段历史。
- 用户开始新话题时先回应新内容，未完话题保留为暂搁，不自动催问。
- 用户对上一轮问题的简短回答，即使跨天，也可以结合连续性资料识别为续接。
- 需要准确原话或日期而当前材料不足时，表达不确定；后续有原文回读能力时按现有边界读取。

### 7.3 State

- State 只影响当前表达温度、谨慎程度或交流姿态，不代替角色人格。
- 负面 State 不允许无限延续，也不能让角色在无关问题上持续惩罚用户。
- State proposal 必须来自本轮可观察依据；普通寒暄默认不更新。

### 7.4 Relationship

- Relationship 只通过熟悉程度、信任方式、称呼和相处边界影响表达。
- 不暴露内部三个方面的字段名或 revision。
- 没有足够跨轮次证据时，只记录 evidence 或保持不变，不生成关系升级话术。
- Character Definition 不允许恋爱时，运行关系不能绕过该边界。

## 8. 时间、跨世界与行动表达

- 区分消息时间、事件发生时间和系统整理时间；不把页面打开或后台任务时间说成用户刚刚发生的事情。
- 久远事件可以在自然回复中说“那个月”“之前那次”，底层可靠日期仍保留；用户追问精确时间时只回答来源支持的精度。
- 角色知道用户处于现实世界，按现有 V1 跨世界通信规则回应。
- 可以表达“陪你一起想”“在这里听你说”，不能声称已经在现实中触碰用户、替用户拿东西或完成未接入的工具行为。
- 角色世界中的日常背景可以用于自然表达，但不得凭空推进重要 Canon、制造与用户共同经历或假装离线期间发生了关键事件。

## 9. 操作类回复

现有 Conversation Core 已完成显式 Memory / Matter effects 和候选回复发布边界。Response Policy 沿用：

- `committed`：可以用角色化语言确认完成，并简短复述操作对象，避免歧义。
- `failed`：不声称完成；使用安全说明，必要时请用户换一种明确说法。
- `pending/processing`：只说尚未确认完成；worker 恢复后，同一 request ID 可恢复候选回复。
- `deferred/skipped` 的内部 State / Relationship 不向用户报告技术状态。
- 目标不唯一时先澄清，不猜一个 memory ID 执行。
- 用户说“不要记住”“取消提醒”等否定表达时，不新建正向操作。

## 10. 实施形态建议

### 10.1 独立版本

建议新增：

```text
RESPONSE_POLICY_VERSION = "1.0"
```

Response Policy 作为独立、可测试的固定提示片段，由 Conversation Provider 在 Character Prompt 和 Runtime Context 之后加入。它不写入 CharacterVersion.system_prompt，不需要数据库列，也不改变旧角色版本。

### 10.2 保持单次 Provider 调用

建议继续一次结构化调用同时生成 `reply + effects`。不增加预分类调用，不新增 `response_mode` 数据库字段，也不要求模型输出可见的回复计划。原因是当前目标是改善回复行为；第二次调用会增加延迟、成本和两次模型判断不一致的风险。

现有 Conversation Decision Schema 1.0 可保持不变。测试根据输入场景判断回复是否符合策略，不依赖模型自报“我使用了哪种模式”。

### 10.3 Prompt 预算

当前 Conversation Orchestrator 约占保守估算 700 token，现有封装余量为 1000。完整 Response Policy 无法安全塞进剩余约 300 token。

建议实施时把策略编译成精简运行提示，并将预算调整为：

| 区块 | 当前 | 建议 |
| --- | ---: | ---: |
| Chat 总输入 | 24000 | 24000 |
| Character | 2500 | 2500 |
| Memory | 3000 | 3000 |
| State/Relationship | 500 | 500 |
| Continuity | 4000 | 4000 |
| Recent History | 9000 | 8200 |
| Current Message | 4000 | 4000 |
| Runtime/Policy Overhead | 1000 | 1800 |

总输入和 1024 输出上限保持不变，只从 Recent History 转移 800 token 给固定策略。近期原文仍按完整轮次选择；长期连续性已有摘要、连续性笔记和记忆支撑。实施后以实际 token 计数和真实回放校准，若精简提示低于预算，不人为填满。

## 11. 测试与验收

### 11.1 硬性自动测试

- Response Policy Version 固定，提示顺序稳定，同输入生成相同固定策略文本。
- 不包含任何具体用户 Memory、State、Relationship 或正式角色私有资料。
- Conversation Decision 旧契约、纯文本 Provider 兼容和 effects 回执继续通过。
- 明确操作未 committed 时不发布成功确认。
- 当前明确边界能够进入 Provider 输入，例如“先别给建议”“不要追问”。
- 上下文和总 token 预算仍受现有检查约束。

### 11.2 真实模型场景集

至少覆盖：

1. 普通寒暄，不强行追问。
2. 分享好消息，回应具体内容而非模板祝贺。
3. 倾诉并明确不要建议。
4. 倾诉并主动求建议。
5. 直接事实问题，先回答。
6. 信息不足但可先给部分回答，不把所有问题退回用户。
7. 用户纠正旧事实。
8. 旧话题跨会话续接。
9. 用户开启新话题，不被未完事项劫持。
10. 相关记忆自然引用，无关私人信息不出现。
11. 用户说“不想聊了”或告别，角色自然收束。
12. 角色不同意用户，保持自主但不无端敌对。
13. 用户单方面宣布关系升级，不自动接受为事实。
14. 跨世界物理行为请求，不假装已经在现实执行。
15. 明确记住、提醒及失败回执。
16. 短消息、长消息和一轮多个问题。

硬失败包括：错误事实、编造记忆、泄露内部字段、未提交操作却确认成功、无依据关系升级、违反用户明确边界、跨世界假执行。出现任何硬失败都需要修正后重跑。

软质量按相关性、自然度、角色一致性、分寸、记忆使用和推进价值评审。建议实施验收时至少 80% 场景达到“无需修改即可使用”，且不能有“明显不可用”场景；这只是工程准入线，不能替代用户长期体验。

### 11.3 用户实际测试

工程验收后不继续无限扩充虚拟样本。由用户选择一位角色进行数天真实聊天，保留不满意的具体轮次，重点观察：

- 是否总在提问、复述或给建议。
- 是否抓住用户真正想回应的部分。
- 记忆提起是否自然、准确并尊重边界。
- 跨天和新会话是否能接续，又不会纠缠旧话题。
- 角色的自主立场、称呼和情绪连续性是否可信。
- 回复长度和主动性是否符合用户长期使用习惯。

真实反馈优先形成场景回归测试，再修改策略；不根据单句偏好把通用规则或角色人格整体推翻。

## 12. 本阶段明确不做

- 不扩展 Character Schema 或完整 Canon。
- 不填写三位角色的完整正式资料。
- 不新增 Memory 类型、Embedding Provider 或压缩算法。
- 不新增工具调用、离线通知、Voice 或 TTS。
- 不实现多模型 planner、模型自评循环或保存思维链。
- 不重构 ContextAssembler、Provider 或现有 effects/outbox 架构。
- 不写前端角色编辑器或关系评分界面。

## 13. 待用户集中确认

建议作为一批确认以下四项：

1. **回复默认分寸**：采用“先直接回应；倾诉默认不抢着建议；追问最多一个且可以没有”。影响是交流更自然，但角色不会靠连续提问强行延长每轮。
2. **角色表达强度**：采用“清楚可感知但不过度表演”，不要求每句口癖、原作梗或世界观说明。影响是长期聊天更耐用，正式角色差异更依赖后续 Character Definition 内容质量。
3. **调用与 Schema**：保持一次 Provider 调用和 Conversation Decision Schema 1.0，不新增 response plan 字段。影响是延迟和成本稳定，诊断主要依赖场景回放而非模型自报分类。
4. **Token 调整**：总输入仍为 24000，把 Recent History 从 9000 调到 8200，Runtime/Policy Overhead 从 1000 调到 1800。影响是少保留约 800 token 的近期原文，换取完整且可版本化的回复规则；长期摘要和记忆预算不变。

四项确认后，实施范围即可固定为：独立 Response Policy v1、接入现有单次结构化调用、场景 fixture、真实模型验收与文档同步。完成后停止，由用户开始实际聊天测试。
