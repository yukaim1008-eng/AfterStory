# AfterStory V1 当前决策基线

- 状态：已确认部分决策，待继续讨论
- 更新日期：2026-09-09
- 用途：记录当前已经确定的产品与技术决策，防止后续讨论或 Agent 实现时发生漂移；本文不是完整开发方案。

## 1. 产品定位

- AfterStory 的核心定位是长期角色陪伴，不是披着角色外壳的通用 AI 助手。
- 用户能够与角色持续进行多轮对话；角色保持人设，形成与用户有关的长期记忆、关系和状态，并以符合角色的方式和声音回复。
- AfterStory 采用“跨世界陪伴”作为默认交互前提：角色仍然认为自己是原作世界中的本人，知道用户来自另一个世界并能够持续通信，但不认为自己是 AI。
- 当前通信方式与双方过去的关系来源需要分开：双方现在可以跨世界交流，但用户在原作中是否拥有玩家身份，由具体角色定义决定。
- 未来可以逐步增加天气、日历等个人助手能力，但工具提供事实或执行能力，角色仍然负责以自身身份和表达方式回应。
- 技术上支持轻量多用户，产品上是一份可以公开分享和自托管的完整作品；V1 暂不按面向大量陌生用户的商业平台建设。

### 1.1 跨世界交流规则

- 角色保留原作身份、世界、经历、人物关系和表达方式，不因为与现实用户交流而退化成通用助手。
- 角色知道用户生活在另一个现实世界，也知道双方通过 AfterStory 建立了可持续的通信连接。
- 角色不了解的现实信息应由用户告知，或在未来通过用户授权的工具获取，不能无依据地假装知道。
- 角色不假装亲身经历用户现实世界发生的事情，也不默认把所有用户视为原作剧情人物；当原作本身存在玩家主角时，可以通过 Character Instance 将用户映射为该玩家身份。
- 原作经历属于 Character Definition；角色与用户通过 AfterStory 形成的新经历属于对应 Character Instance 的 Memory、State 和 Relationship。
- 未来接入天气、日历等能力时，工具负责提供事实或执行结果，角色仍然以自身身份自然表达，不直接暴露 API、数据库或内部工作流。

### 1.2 V1 主角色与关系来源

- V1 主角色确定为《异环》的娜娜莉。
- 当前用户在娜娜莉的原作关系中映射为游戏里的“鉴定师”，不是第一次认识她的跨世界陌生人。
- 娜娜莉与用户已经拥有原作中共同冒险、并肩行动的伙伴关系；AfterStory 承接这段关系继续发展。
- 当前通信仍然属于跨世界交流，但双方的关系来源是原作世界中的玩家伙伴关系。
- 双方在 AfterStory 中产生的新经历必须与原作共同经历分开保存。

## 2. V1 范围

V1 包含：

- 一个完整主角色和少量用于验证通用性的测试角色。
- 文字输入和角色化文字回复。
- 稳定的多轮会话和会话持久化。
- 长期记忆的提取、保存、语义检索和上下文注入。
- 角色状态与用户关系随对话持续变化，并实际影响回复。
- 结构化的角色回复结果，以及独立的语音生成流程。
- 角色绑定 Voice Profile，通过 TTS 生成并保存语音回复。
- 用户、角色实例、会话、记忆、状态和音频之间的隔离。
- 对角色一致性、记忆召回、状态变化、数据隔离和 TTS 失败降级的验证。

V1 不包含：

- 用户角色创建器。
- 天气、日历等工具调用。
- LangGraph。
- 微信接入。
- ASR、实时语音输入、VAD、打断和全双工语音。
- 角色社区、角色市场和面向大量用户的运营能力。

## 3. 角色类型与身份规则

- 精选角色：由项目提供并经过完整测试，行为相对稳定。
- 自定义角色：由用户创建，代表该用户对角色的理解，不承诺与其他同名角色一致。
- 精选角色与未来的自定义角色必须使用同一套 Character Definition 规则，不能为主角色编写一套写死在代码里的特殊实现。
- `character_id` 决定角色身份，角色名称只是展示用代号，允许重名。
- 用户创建或 Fork 出与现有角色同名、但定义不同的角色时，应使用新的 `character_id`。
- 角色资料更新需要保留版本概念；`character_version_id` 表示某一版具体定义，不能用名称代替版本。
- `character_instance_id` 表示某个用户与某个角色建立的具体关系实例；Memory、State、Relationship 和 Conversation 均绑定到该实例。
- 数据模型允许一个用户未来为同一角色创建多个相互隔离的实例或存档；V1 默认只使用一个主实例，暂不开发复杂的多存档管理界面。

### 3.1 原作经历更新规则

- 每个精选角色必须拥有一个最低 Canon 基线，不能从完全空白的原作经历开始。
- 最低 Canon 基线表示使用该角色所必须承认的基础原作经历和关系，也是 Character Instance 能选择的最早剧情进度。
- 最低 Canon 基线、默认 Canon 进度和最新可用 Canon 进度需要区分，不能只保存一个模糊的“当前版本”。
- 原作持续更新时，应新增带版本或剧情节点标识的 Canon 内容，不直接覆盖旧内容。
- 每个 Character Instance 保存自己当前采用的 Canon Checkpoint，不同用户可以停留在不同剧情进度。
- 系统可以提示存在新的 Canon 版本，但不能默认强制更新；用户确认已经了解相应剧情后，再手动更新当前实例，以避免剧透和时间线错乱。
- 原作中鉴定师与娜娜莉共同经历的内容属于 Canon Experience；AfterStory 对话中形成的个人经历属于 Personal Memory，两者来源和更新方式必须隔离。
- V1 只需要支持一个经过确认的娜娜莉最低 Canon 基线和当前默认进度，不在本阶段实现自动抓取、自动理解剧情或复杂内容管理后台。
- 娜娜莉的最低 Canon 基线最终选择 1.1、1.2 或某个更准确的剧情节点，留到角色资料与数据来源阶段单独确定。

## 4. 三个核心领域

### 4.1 Character System

负责回答“角色是谁”，保存相对稳定的角色定义，例如身份背景、性格、价值观、行为边界、说话方式、人物关系、世界观、示例对话、初始状态和默认 Voice Profile。

Character Definition 不保存某个用户的私人记忆，也不保存某次会话产生的实时状态。

### 4.2 Conversation Core

负责回答“角色本轮如何理解并回应”，包括加载角色定义、最近历史、相关长期记忆和当前状态，生成结构化回复，判断状态变化和记忆候选。

“角色的思考方式”指可设计和验证的上下文组织、回复策略、状态变化与记忆读写规则，不依赖保存或暴露模型内部思维链。

Conversation Core 输出框架无关的 Character Response，至少需要承载回复文本、情绪、说话风格、状态变化和记忆候选；具体字段仍待后续设计。

### 4.3 Voice Layer

负责回答“角色如何把内容说出来”，只接收 Character Response 中需要朗读的信息和角色 Voice Profile，再调用具体 TTS Provider。

Voice Layer 不决定角色人设、长期记忆和关系变化。更换 TTS Provider 不应要求修改 Character System 或 Conversation Core。

## 5. 数据归属与隔离

- Character Definition 可以被多个用户使用。
- Character Instance 归属于一个明确用户，并引用一个明确的 Character Definition 版本。
- Character State、Relationship、Conversation、Message 和 Memory 必须归属于明确的 Character Instance。
- 同一精选角色被不同用户使用时，双方的记忆、状态和关系不能互相访问。
- 同一用户使用不同角色时，角色之间的记忆和状态不能串联。
- Voice Profile、TTS 结果和音频记录必须绑定正确的角色或角色实例，不能因缓存或复用产生跨角色串音。
- V1 验收需要包含跨用户、跨角色和跨实例的数据隔离测试，不能只验证正常接口返回。

## 6. 工作流与未来 LangGraph 边界

- V1 使用普通 Python 应用服务实现清晰、固定的对话工作流，不为使用框架而提前引入 LangGraph。
- Character Definition、Character Instance、Memory、State、Provider、Repository 和对外接口模型必须保持框架无关。
- LangGraph 将来只允许进入流程编排层，不得让 LangGraph AgentState 同时充当数据库模型、领域模型和 API 返回模型。
- 当系统加入工具选择、条件分支、执行确认、失败重试或暂停恢复后，再评估是否引入 LangGraph。
- 后续切换 LangGraph 时，应复用现有角色、记忆、状态、Provider 和 Repository 能力，只替换或扩展工作流编排。

## 7. 技术基线

- 前端：Vue 3 + TypeScript + Vite。
- 前端实现顺序：先预留位置，V1 后端核心链路完成并验收后，再单独完成页面结构、交互原型和视觉设计，之后开始前端开发。
- 后端：Python + FastAPI。
- 数据库：PostgreSQL。
- 向量检索：优先在 PostgreSQL 中使用 pgvector，最终接入方式仍需在 Memory 设计阶段验证。
- 数据访问与迁移：倾向使用 SQLAlchemy 和 Alembic，具体配置待工程骨架阶段确定。
- V1 编排：普通 Python 工作流。
- LLM、Embedding 和 TTS 必须通过独立 Provider 边界接入，具体供应商与模型仍待确认。
- 音频 V1 可以先使用本地存储，但必须通过存储边界隔离，方便未来更换对象存储。
- 当前 `.env.example` 中的 SQLite 配置只是早期草案，与已经确认的 PostgreSQL 决策不一致，搭建后端骨架时需要修正。

## 8. 前后端实施顺序

- 后端先行，前端暂不开发业务页面。
- 前端目录可以预留，但不能为了占位提前生成大量模板代码或组件。
- 后端阶段仍需定义清晰的前端数据契约，使一轮回复能够表达文字、情绪、状态变化、音频状态等前端需要的信息。
- 后端核心链路完成后，先做前端页面结构、交互原型和视觉规范，再由 Agent 实现 Vue 页面，避免边开发功能边堆叠界面。

## 9. 外部渠道与工具的后续方向

- Web 是 V1 的唯一正式交互渠道。
- 微信接入不属于 V1；后续首次接入时，优先考虑将 OpenClaw 与腾讯微信渠道插件作为独立消息网关，而不是把 Character Runtime 建在 OpenClaw 内部。
- Character Runtime 需要保持渠道无关，未来由 Web、CLI 或微信 Channel Adapter 转换成统一的输入与输出模型。
- V1 跑通后，优先尝试天气查询等只读工具，再逐步考虑日历读取和有副作用的日历操作。
- 工具权限归属于用户或用户的角色实例，不能仅凭导入角色定义自动获得日历、文件或其他私人数据权限。

## 10. 角色素材与公开仓库边界

- 开发和个人使用阶段可以使用熟悉的游戏或动漫角色验证角色表现。
- 公开仓库应尽量保持核心引擎与本地角色素材分离，立绘、参考音频、克隆模型等资源是否公开在发布前单独检查。
- 用户本地角色资料和语音资产应通过独立目录与 `.gitignore` 管理，不能默认提交到仓库。
- 具体主角色、采用的角色时期、资料来源、初始关系和公开范围仍待确定。

## 11. 尚未确定

- 娜娜莉最低 Canon 基线最终采用 1.1、1.2，还是使用更准确的主线剧情节点。
- 娜娜莉原作资料、台词和语音等数据的具体来源、采集方式与验证标准。
- 娜娜莉与鉴定师伙伴关系在 V1 中对应的具体初始状态和关系强度。
- 测试角色的选择和差异维度。
- Character Definition、Character Response、State 和 Memory 的具体字段。
- LLM、Embedding、TTS 的首选供应商、模型与降级策略。
- PostgreSQL 与 pgvector 的本地启动和部署方式。
- 用户认证方式。
- 音频文件的生命周期和清理规则。
- V1 前端页面、视觉风格和移动端适配范围。
- 熟悉角色相关配置与素材在公开仓库中的最终发布边界。
